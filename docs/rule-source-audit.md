# 规则命令源节点审计

规则／事件／命令关联之外，即时输出需要保留产生它的准确源节点标签。标签描述被接受的程序节点，不证明现场动作成功，也不证明某条外部反馈由该节点引起；不能据此改变鉴权、控制范围或反馈真值。

## 即时与延迟边界

`EventRules` 和执行模式 `PanelRules` 经 `PreparedRule` 将标签按逻辑命令次序带入 Admission。混合延迟规则经 `deferred_rule` 对其中的即时命令使用同一路径。组合灯展开时，每一条继电器／调光物理命令复制所属逻辑节点的标签，随后独立节点仍保留自己的标签；不能按设备类型或展开前的命令数量重新配对。

延迟场景原有的调用节点、成员节点、`scene_cause`、`scene_step` 和软件渐变样本来源保持原行为。即时规则来源存储在 `rule_command.source`，通过命令 ID 与队列日志关联，由 `Store::rule_chain` 返回 `CommandResult.source`。

## 准入与事务

存在来源向量时，必须存在规则审计，向量长度必须等于对应命令数量。每批至多 128 条，单个标签为 1–8192 UTF-8 字节。Admission 在逻辑展开前校验，Store 在物理展开后再次校验；数量不符、空标签、超长标签或无审计的来源均拒绝。

队列命令、规则／事件审计、逐命令来源、变量 CAS、场景启动及取消记录共享原事务。来源插入失败或变量版本冲突不能留下部分收据、变量改变或取消结果。该字段不引入新的运行、订阅、重试或重放能力。

## 重复目标的有序节点

带持久规则审计的批次允许同一逻辑目标出现多次，每个节点独立展开并复制自己的来源，不按最终状态删掉相同节点。专用 Arbiter 入口要求全部命令属于 Rule、同一非零运行 ID，然后复用逐命令策略、容量检查和原事务；相邻的立即 Level 命令不合并。外部 HAP／HTTP 和无审计内部批次保留重复意图拒绝，默认队列入口继续原合并行为。不同请求的人工覆盖、运行取消、STOP 优先级、失败后停止剩余输出及重启不重放保持。

逻辑设备及组合灯供电关系继续使用稳定 `module_id + channel` 引用；真实 RS485 地址只在模块注册表和当前代次的传输解析中使用，不嵌入规则、场景或组合灯对象。

有序输出证明这里只到合成总线写出；它不能替代原始程序条件、变量、延迟与现场行为的完整审核。参见[有序输出限定证据](evidence/stage-d-study/rule-order-check.json)。

## schema 25 与历史兼容

数据库从 schema 24 升为 25，增加可空的来源列。升级前应保留一致性备份；旧程序不能直接打开 schema 25。备份检查支持 schema 18–25，读取旧备份时不迁移它。

升级无法重建曾被丢弃的标签，历史行保持 `NULL`，API 返回 `None`。既有无标签的可信内部接受接口仍保留，读取这些记录明确为来源未知；不能把规则 ID、设备类型或当前配置当作历史源节点。现有延迟场景的来源不会被该迁移替换。

验收使用合成规则、schema 2 固定模块／通道、内存 actor、SQLite 重开及 localhost 服务；现场程序、原项目 XML、身份、凭据和日志不进入公开仓库。来源审计只证明节点关联，不能替代客户端、物理 LED、窗帘或网络的现场确认；已完成范围见[结项清单](control4-takeover-checklist.md)。
