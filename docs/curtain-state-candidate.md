# 窗帘状态模型候选

本候选是可审查的软件实现，当前服务尚未安装它。既有 Web、HAP、字段配置、原控制系统和未批准的源程序保持不变；本轮没有部署或实物动作。

## 手动动作与状态

Opening、Closing、Stopped 是互斥的动作估计；Open、Closed、Intermediate 是独立的位置类别。未知用缺少有效依据表示，不增加第四种命令。observed 与 inferred 分开保存，命令／计时和百分比都明确为 Inferred，不能写入模块实际 ground truth。

所有有效的主动 Open、Close、Stop 都经原校准、鉴权和唯一所有者提交。估计终态、历史同方向、自动条件或绿灯不用于手动去重或禁用；即使电机可被外部手动移动，每次新手动请求仍重新发送并从新 Written 重新计时。本模型没有外部手动运动的可靠读回，不能宣称侦测了它；已知干预可明确失效估计，未被侦测的干预可能使缓存估计不准。

停止按钮始终可供有效手动请求使用，但仍受校准、权限、连接、容量等原入口门禁约束。`stop_led_active` 只表示 LED／视觉活动提示，与停止按钮可用性及“当前命令为 Stop”分开。成功 Written 的 Open／Close 使活动提示为红；成功 Stop 或估计到位后，经过已配置提示延迟变绿。未配置延迟时不猜自动变绿时间；提示不直接发送面板命令。

## 可配置计时与百分比

`Timing` 分别保存 `open_travel_ms`、`close_travel_ms`、`stop_led_idle_ms`；通用默认均为 `None`，有值须为 1 毫秒至 24 小时。某方向没有行程配置时不推断到位，且不能按速度计算该方向百分比。互锁／吸合参数、参数查询结果和没有回复都不自动成为行程或运动观测。具体本地近似值及审批范围只保留私有候选建议，不自动应用现场配置。

计时锚点是持久命令日志的同 boot／全代次、同设备和同校准命令的 **完整 Written 单调时刻**，不是接受或首次读取时刻。首次读取已晚于行程时应立即得到相应估计终态；提示延迟也从真正 Stop Written／行程终点算起。当前位置需要可靠的起点和已配置全行程，按恒速假设计算，以百分比的百分之一为数值精度并夹在 0–100%；这些条件成立也仍是估计。

新方向或 Stop 接受时取消旧的终态计时器，但旧运动轨迹保留到新命令真正 Written 的边界。Stop 排队期间不提前冻结位置；反向时先计算旧方向到新 Written 的位置，再由该估计起点重新计算。连续 Stop 不重复累计运动。中途 Stop 且起点未知时只保留 Intermediate，数值为未知，绝不补 50%。有可靠起点时保留按运行时长计算的中间百分比；后续方向从此推断起点继续计算。无中途 Stop 时经过本次配置的完整方向行程推断终态，重复同方向命令也重开完整计时，不因缓存终态立即“到位”。

日志转为 Observed 后 `updated_ms` 不再是 Written 时刻。如果先前已核对并保存 Written 锚点，可以继续用它；如果首次只看到 Observed 而缺失真实 Written 锚点，则估计回到未知，不能拿较晚时间补造运动。模块没有已验证的实际运动／位置链路时，原始反馈仍未知；虚拟动作复位、进程退出和成功网络写出也不是实际 Stopped。

## 生命周期与条件策略

命令具有不透明 ticket、单调 ID、实例内序号和 boot／连接／配置／控制代次。旧回执、旧定时结果、失败、不确定、取消、断流、授权失败、外部干预、放弃 future 和重启不能恢复旧估计或重放动作。配置／映射变更需要重新构建候选，不能沿用旧实例解释新通道。候选读状态不产生动作；已接受后无法安全跟踪仍报告接受的 ID 和 `projection_tracked=false`，不诱导重试。

`cached` 是 `captured_ms` 时刻的诊断副本，当前估计须经 `refresh` 重新核对所有者、收据和代次。核心 `observe` 仅预留给独立可信的实际提供者；当前适配器不调用它，不把任何估计或参数查询提升为 Observed。

默认自动条件只采用新鲜实际 Stopped；明确设置 **单个本地候选** 的 `ReviewedLocalEstimate` 后，可采用有效且标明 Inferred 的估计 Stopped。许可不作为全屋默认，不提升实际 ground truth，不启用原程序。先前“Stopped／前一命令非 Open”审查谓词仅保留给独立自动条件，**不阻挡主动手动按键、Home 或 Web 请求**。原变量其他编码、初值、更新和持久化时机以及事件／LED 执行归属仍须审核，本地 `last_written` 只是审计诊断，不是原系统变量。

## 既有入口的接入方案与下一软件增量

先接入已授权手动 HAP／Web，原面板程序和自动规则仍保持禁用。每个稳定逻辑窗帘只由运行时管理器持有一份轨迹；HAP、Web 和将来获准的手动面板事件共用它，不能各自创建互不知情的计时器。

1. 在 `RuntimeMotorHap::Handler` 和 `management_devices` 的 Open／Close／Stop 分支复用其现有主体／设备授权和校准入口，将成功接受的逻辑动作交给统一管理器。每次有效点击新建请求，保留现有 HTTP 同 request_id 的幂等回执；不按缓存位置、动作或 LED 去重，不改变 false HAP 复位的无动作语义。
2. 在统一服务监督循环、HTTP／HAP 锁外核对真实 Written 收据并推进估计，配置发布／断流／退出时失效管理器。`RuntimeMotorHap::flush_resets` 保持接受确认，不把虚拟动作复位当作停止。Web 的复连只读同步不重放任何手动请求。
3. Web 增加独立的 `motor_estimate` 与来源／时间，保持 `observed` 为模块实际数据；显示“估计中间／估计百分比／估计到位”，断流或未知起点明确不可用。Motor 不套用普通灯的 On／Off 对称禁用；Stop 始终可在原权限和安全门禁下提交。HAP 先维持三个动作入口，不把百分比填入声称实际位置的 WindowCovering。活动提示与 Stop 动作特征分开，避免红灯导致点击 false 仅复位而未发 Stop。
4. 只有明确审核的逻辑 LED 绑定与执行归属才能加入同步。计划用同所有者 `submit_panel_led`、手动模式验证和当前代次的去重收据，按成功 Written 后的红／绿边沿输出；未知／失败不能伪造已停止绿灯。默认无绑定时只产生诊断提示，不发送 LED，也不抢占原系统。
5. 下一增量用真实 localhost 加密 HAP＋Web 与内存总线联合验证每次手动重复动作、实际 Written 边界、统一轨迹、LED 逻辑入口、发布／断流／撤权和无重放，再独立审查后安排限定现场窗口。原源程序语义、变量及事件所有权不因手动接口接通而自动获批。

本轮已提供核心模型、真实收据读取及校准单窗帘适配器；上述运行循环／HAP／Web／LED 接线是明确的下一软件增量，尚未声称已安装或现场通过。
