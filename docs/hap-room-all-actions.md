# 房间“全部”的 HomeKit 状态与动作

房间“全部”按实际负载显示：任意灯亮时为开启，所有灯灭时为关闭。HomeKit 写入开启时执行已审核的全开配方，写入关闭时执行完整关闭配方；重复写入同一个值不能反向切换。

这与 App 的相对点按以及实体面板的明确全开／全关分别处理。原始场景、墙键绑定和关闭共享通道的规则不因 HAP 显示调整而改变，也不按名称猜测开关语义。

## 显式绑定

在已审核的 `scene_tracking` 策略上增加可选的 `hap_action`：

```json
{
  "scene": "room-all",
  "hap_activity": false,
  "hap_action": {
    "on_scene": "internal-room-full-on",
    "off_scene": "internal-room-shutdown"
  },
  "aggregation": "any"
}
```

此片段是策略的新增字段，不能作为完整配置直接导入。策略仍需原有启用状态、物理成员、时效、待确认规则和审核依据。开关配方须已启用、审核、隐藏且与公开入口同房间；缺失、自引用、链式绑定、相同开关配方、多个入口复用同一配方或同时分配第二张活动卡片均拒绝。

公开场景 ID 继续作为 HAP 配件键，保持已分配的 AID／IID。实际负载状态直接投影到这张卡片，不新增另一张只读状态卡片。授权检查公开入口后，才提交配置指定的绝对配方；调用者不能自行指定替代目标。

内部开关配方继承公开入口的模式反馈确认规则，不能因新增隐藏 ID 而提前提交模式变量。开启和关闭都须遵守原有写出及物理反馈条件；这一映射只用于确认身份，不扩大配方动作或调用者权限。

读回使用运行时已有的反馈和权威校验，不发送总线查询。房间负载状态走专用批读，不重复加载完整场景目录；物理证明每批最多32条，并保留逐策略的待确认、新鲜度和权限判定。未知、待确认、过期或运行时不可用不能当作关闭。端点构造时不等待尚未运行的控制事件循环；启动后由投影任务获取状态并推送变化。

命令已持久受理后，紧随其后的状态读取超时不能把这次写入改报为失败，也不能触发控制重发。此时保持状态不可用，等待正常投影恢复。物理写出按原截止时间执行；同一阶段的剩余报文在一个有界的准入轮次中领取，避免逐帧往返被目录读取占用。

## 发布范围与房间归属

未明确选择灯光的旧场景／窗帘端点继续维持原范围，新增灯光需通过显式桥接计划。完整发布清单只采用 App 可见灯光和公开场景，内部配方不作为用户卡片发布。

Apple 的房间归属由 HomeKit 家庭管理。服务器端配置的房间字段不等于 Apple「家庭」已分房；自动同步需由获授权的原生 App 调用 `HMHome.assignAccessory`。当前 App 未包含此权限和同步功能，不应声称发布后已经自动归房。已有配件和房间归属应保留，不通过删除桥接器重新配对实现迁移。

参考：[Apple 房间分配 API](https://developer.apple.com/documentation/homekit/hmhome/assignaccessory(_:to:completionhandler:))、[桥接配件不会自动继承桥接器房间](https://developer.apple.com/documentation/homekit/hmaccessory/isbridged)。

## 验证边界

回归覆盖任意单灯状态、全部熄灭、重复开启／关闭、未知状态、未授权写入以及配置拒绝。整套私有配置另外通过真实 CLI、模拟 TCP 网关与加密 HAP 控制器验证；原始映射、配置、报文、失败记录和制品指纹留在私有验收目录。

软件和隔离验证通过不代表已发布或已完成 Apple 客户端现场验收；以部署结果和现场记录分别确认。

当前灯光资格覆盖逐个逻辑灯控制。同一 HAP 请求混合多个逻辑灯，或混合逻辑灯与继电器，仍会整体拒绝；房间级批量控制还需共享资源的联合规划，不能把这些拒绝测试通过描述为完整支持。
