# 房间“全部”的 HomeKit 状态与动作

房间“全部”按实际负载显示：任意灯亮时为开启，所有灯灭时为关闭。HomeKit 写入开启时执行已审核的全开配方，写入关闭时执行完整关闭配方；重复写入同一个值不能反向切换。

这与 App 的相对点按及实体按键规则分别处理；实体规则见[目录与全部](scene-catalog-consolidation.md)。HAP 明确写入不能按名称猜测或反向切换。

## 显式绑定

在已审核的 `scene_tracking` 策略上增加可选的 `hap_action`：

```json
{
  "scene": "room-all",
  "hap_activity": false,
  "hap_action": {
    "on_scene": "internal-room-full-on",
    "off_scene": "internal-room-shutdown"
  },
  "aggregation": "any"
}
```

此片段展示策略字段，不能作为完整配置直接导入。策略仍需原有启用状态、物理成员、时效、待确认规则和审核依据。开关配方须已启用、审核、隐藏且与公开入口同房间；缺失、自引用、链式绑定、相同开关配方、多个入口复用同一配方或同时分配第二张活动卡片均拒绝。

公开场景 ID 继续作为 HAP 配件键，保持已分配的 AID／IID。实际负载状态直接投影到这张卡片，不新增另一张只读状态卡片。授权检查公开入口后，才提交配置指定的绝对配方；调用者不能自行指定替代目标。

内部开关配方继承公开入口的模式反馈确认规则，不能因新增隐藏 ID 而提前提交模式变量。开启和关闭都须遵守原有写出及物理反馈条件；这一映射只用于确认身份，不扩大配方动作或调用者权限。

对于阅览室这类以完整灯光组合判断状态的场景，可以显式指定 `hap_action.readback: "all_conditions"`，并保持策略 `aggregation: "all"`。只有所有条件都满足才显示开启；这不改变房间“全部”的任意灯亮规则。其隐藏开／关配方必须是立即执行的完整灯光和LED命令，与原公开程序具有相同输出范围。开启配方须满足每条状态条件，关闭配方须将范围内灯光全部关闭；缺少通道、增加目标、条件式配方、间接调用、渐变和变量赋值均拒绝。涉及共享供电和模式记忆的程序仍需单独审核，不能套用这个简单负载模型。App和墙键继续执行原相对程序，HAP重复开启／关闭则执行明确的绝对配方。

卧室这类需要保留模式身份的场景，可在已有 `scene_component_activity` 上配置 `hap_action`，并显式使用 `readback: "confirmed_component"`。HAP复用原组件的实际写出、反馈、变量版本及请求来源证明；持久化的模式值和相同灯光外观不能建立开启状态。新请求受理后仍为待确认，直到本次写出与反馈完成；重复开／关使用审核后的独立绝对配方，App和墙键保留原程序。

组件配方须隐藏、同房间且具有独立ID，不能与其他入口复用或串接。条件、变量赋值和立即灯光／LED命令仅能使用原公开程序已有的读取范围及操作，不允许新增目标、变量赋值、间接场景调用、查询、窗帘命令或渐变。每份配方须有对应组件变量的赋值和实际灯光操作；这类静态约束仅证明范围，配方须逐项验证绝对开／关和共存模式的行为。原组件ID只用于反馈确认，不成为隐藏配方的授权别名，原有场景授权及指示灯派生授权规则不变。

已有 `scene_presentations` 的公开场景复用其审核后的内部模式状态：HAP 只创建公开入口卡片，读取对应模式的确认状态，写入仍执行公开入口自身的明确开启／关闭分支。不会为内部模式再创建卡片，也不会把内部模式 ID 当成授权别名。同样灯光组合的不同模式仍按各自确认来源区分；未知和待确认继续显示不可用，不能回落成关闭。

读回使用运行时已有的反馈和权威校验，不发送总线查询。房间负载状态走专用批读，不重复加载完整场景目录；物理证明每批最多32条，并保留逐策略的待确认、新鲜度和权限判定。未知、待确认、过期或运行时不可用不能当作关闭。端点构造时不等待尚未运行的控制事件循环；启动后由投影任务获取状态并推送变化。

命令已持久受理后，紧随其后的状态读取超时不能把这次写入改报为失败，也不能触发控制重发。此时保持状态不可用，等待正常投影恢复。物理写出按原截止时间执行；同一阶段的剩余报文在一个有界的准入轮次中领取，避免逐帧往返被目录读取占用。

同一传输批次已完整写出的操作，也在一个有界准入轮次中确认，并把对应日志与亮度设置一起提交。每批仍最多32帧，原写入租约不延长；部分操作和未发送后缀不计为完整写出，后面成员无效时不能部分提交前面的回执。这减少逐帧重复运行审计的开销，不改变反馈确认与重试规则。

## 发布范围与房间归属

灯光、场景和窗帘通过显式桥接计划选择，未选入的配件不自动发布。完整发布清单只采用 App 可见灯光和公开场景，内部配方不作为用户卡片发布。

Apple 的房间由 HomeKit 管理。使用具有 HomeKit 签名能力且已获用户授权的原生 App，读取桥接清单、匹配桥、预览并应用归属；也可在 Apple「家庭」手动编辑。不要通过删除原桥重新配对来调整房间。详见[房间分配](homekit-room-placement.md)。

桥容量与单次控制数量分别校验，不能从场景选择上限推导完整配件容量。当前部署使用单座「HomeSense」桥，既有配对、AID／IID 和房间保持稳定；同一身份不能同时由两个运行主机广播和控制。

## 联合控制与全屋入口

单次 HAP 请求包含多个逻辑灯，或同时包含逻辑灯与独立灯光继电器时，由一个联合规划器读取完整资源反馈并一次准入。各组共享资源同时求解，未请求的灯按已有共享规则保留；同一调光通道的不同非零目标、重复目标、隐藏物理资源旁路以及缺失反馈均拒绝，不能先提交一部分。准入时重新校验整组反馈证明、配置版本、配对身份与授权。

联合队列提交不代表 RS485 的物理原子事务。实际报文仍按先断供电、设置直接亮度、再接通供电的顺序发送，并等待正常反馈。联合控制须以对应源码与制品验证共享冲突、反馈变化、无前缀写入及实际 HAP 入口，不能用逐灯控制替代联合验证。按当前`AGENTS.md`，全套测试与回环模拟统一在开发本机执行，目标仅接收生产Release ELF并做必要的启动、健康和只读部署验收。

完整模块的联合开启在发送层压缩：同一已准入阶段内，连续八个命令明确覆盖同一模块的1至8路，且均为开启／立即100%时，R8I8-DIN PRO使用 `AE ID 00 F1 EE`，AD8-DIN使用 `AE ID 00 64 EE`。不从缓存补足缺少的通道，不扩大到未请求的排风扇等负载；中间亮度、渐变、部分通道、其他型号和跨批次命令均保留逐路格式。每路授权与持久化日志保留，完整五字节写出后才能一起记为Written；不足五字节时八路均为部分写出，不能误记成功。状态仍依实际反馈确认，保留原32操作上限、连接代次、权限与截止门禁。

普通灯光联合请求最多10盏（按归并后的逻辑灯数量计数，开关与亮度属于同一盏）；超过10盏在准入前整体拒绝，不拆分后执行前缀。大范围的明确全开／全关使用独立场景入口，不能借普通联合请求绕过上限。实体全开／全关按各自显式规则执行，见[场景目录](scene-catalog-consolidation.md)。完整八路明确关闭也压缩为R818的 `AE ID 00 F2 EE`、AD8的 `AE ID 00 00 EE`；每路的日志、授权和真实反馈要求不变。

全屋场景通过已审阅的 `away_off` 模块范围登记两项显式别名：`whole_house_on_scene` 和 `whole_house_off_scene`。两项必须是独立的绝对即时配方，逐路覆盖同一完整范围一次；开启使用继电器吸合和AD8立即100%，关闭使用断开和0%。全屋关闭的原生App和HAP入口均转交现有离家执行器，保留最高优先级、真实反馈、受限重试和错误告警；墙面离家继续复用这同一执行器。关闭不能嵌入普通规则或与其他场景批量混发来绕过管理流程，重复关闭不触发开启。当前全屋范围为七个R818与五个AD8的全部96路，包括已明确批准的排风扇；不含窗帘。

全屋重复触发由同一个准入执行器限流，App、HAP和实体离家按键不能相互绕过。同方向的新请求至少间隔5秒；未写完的全屋开启、仍在执行或重试的全屋关闭不重复入队。全屋关闭可立即抢占全屋开启；关闭之后再次开启仍需等待5秒，避免交替点按造成连续开关。被限流的请求返回忙，不延迟排队或稍后自动重放；失败的授权／准入不会消耗间隔。离家执行器内部已授权的反馈重试不经过新请求限流，保留原截止时间与错误上报。代次切换使旧限流记录失效，不能恢复旧操作。

全屋开启允许忽略已经达到目标的完整模块：八路都必须是当前反馈代次内的新鲜实测值，R818全部吸合，AD8全部100%。仅有部分通道开启、低于100%、未知或过期均不能省略模块。省略所依据的样本在准入时再次校验，期间发生反馈或未完成写入则不能沿用旧证明；原全屋范围的授权仍须完整满足。全部模块已符合时返回受理但不产生控制命令，也不消耗一次实际开启的冷却间隔。全屋关闭不采用此优化，仍由离家执行器明确关闭并核对本次反馈。
