# 管理控制的精确来源授权

下述授权、发布与安全 STOP 修复已通过本机完整软件检查，尚未部署，也不改变原控制系统的范围。网关持续服务故障隔离、其他管理变更和现场验收分别核查。

## 固定反例

原普通 HTTP 控制只保留 controller 和入站时的权限快照；同 controller 仍被运行时认可，并不证明发起请求的凭据或 Cookie 会话继续有效。固定合成反例中，10 个合法对照通过；在 HTTP 授权后、运行时处理前或接纳后派发前，单独降低角色、移除设备／场景范围、撤销发起凭据或登出发起会话，80 个组合仍产生报文和 Written。反例使用内存线路与独立数据库，不接触真实设备；旧反例源与失败证据独立保留。

## 授权契约

普通设备开关／调光／组合灯／已校准电机、模块单路控制与查询、手动场景／相对场景和运行取消，保留该次请求的精确凭据 generation；Cookie 还绑定精确会话及有效期。来源在异步模块绑定／查询预检前捕获，后续不会通过重新查找令牌而借用替换 generation。内部证明绑定 controller、配置 revision 和原逻辑操作内容，客户端不能提交、序列化或更换这份证明。

一次凭据配置更新总会更换 generation，旧请求及其未完成后效均取消，即使新 grant 仍允许同一目标。这是保守的在途取消政策；不表示降为 member 后仍在范围内的**新请求**失去普通控制权。单独撤销一个来源不会撤销同 controller 下另一份凭据。Cookie 登出仅使该会话的旧工作失效。

证明随接纳队列、时间线、嵌套即时场景、变量／场景结果级联、软件渐变、原生场景后续阶段和审核的窗帘提示 LED 后效传递。内部物理展开保留原逻辑授权：组合灯不要求额外授权隐藏供电端点；合法的 scene-only grant 不要求逐个列出场景内设备或审核的嵌套动作。它不会扩大来源可主动提交的其他逻辑操作范围。可信本地生产者、HAP 与其原有授权契约独立，不借此自动获得新的 Web 来源。

接纳队列与变量提交、原生切换阶段账本及选择完成投影，在源凭据／会话读锁内完成。派发再次检查，唯一传输 owner 在实际同步写期间也持有该来源读锁。已完成撤权后，尚未开始的写入必须为零字节；已经进入有界同步写的动作可以先于撤权完成，不承诺收回已经写出的字节。

尚未派发的已撤权命令取消，其时间线、渐变与派生会话停止未来动作，并保留已写出部分与取消审计。清理只撤销工作、释放预算和记录既有结果，不用管理员身份补发动作。若撤权发生在取得 Writing 票据以后、实际同步写以前，保留既有保守失败／恢复流程：零字节拒绝，结果不伪报 Written；传输 owner 显式恢复后，合法新来源才继续。不会自动重试被拒绝动作。

## 验证范围与状态

- 原固定 80 个零报文／零 Written 负例与 10 个正向对照保持；每个负例之后另核对新 root 请求返回的 command_id 自身达到 Written，并看到预期帧，避免把旧队列残留当作健康对照。
- 取得实际派发票据后撤权，覆盖普通设备、模块和场景；拒绝写出后显式恢复，核对合法新来源自己的命令。
- 首次合法 Written 后再撤权，验证延迟步骤、嵌套即时场景／场景结果／变量级联、渐变采样、相对场景后续查询和窗帘延迟 LED 后效；同时保留不撤权的正向路径及逻辑 scope 约束。
- 异步模块预检期间更新为权限相同的新 generation：旧请求不能重捕获它，新请求可以按保留的权限正常执行。
- 冻结 v5 的完整 workspace／all-targets 为 1086 项、167 个实际测试程序全部通过，无失败、忽略或过滤；原 1067 项保留，新增 19 项。文档检查覆盖 10 个 crate（无示例），严格 Clippy 通过。213 条专项场景记录已包含在全量中，不另加测试总数。见[完整核查](evidence/stage-e-browser/source-authorization-v5-root-check.json)。

## 发布队列与安全 STOP

配置激活／发布已完成旧版反例与修复对照：受理前 12 种失权来源均被拒绝进入屏障，受理后 16 种 STOP 清理与提交路径均完成。API 的管理员来源证明绑定精确凭据 generation、可选 Cookie 会话、expected revision 和两个候选文档的摘要，随 `automation_publication::Pending` 排队。TCP 与模拟协调器预检会丢弃失效来源，Admission actor 在真正进入发布屏障的同一同步临界区持有来源读锁重查，避免预检与入屏障之间的撤权间隙。同 controller 的另一凭据不能替代该来源；缩小范围即使保留管理员角色，也会使旧 generation 失效。

新的合成探针通过真实 API→草稿库→Publisher 队列，保留同 controller 的 root 凭据：分别在请求排队后、已取队列请求后及最后一次队列检查后改变发起来源，要求不得进入屏障或提交；新 root 请求必须提交自己返回的候选 revision。另在屏障成功建立后撤权，要求原有已排队 STOP 实际写出、原子提交并用新代次模拟连接完成读取恢复，不因撤权留下半切换状态。STOP 对照包含受信任本地来源和与发布请求同一凭据／会话的来源，并分别在派发票据前、票据后到同步写入前改变来源。

成功进入屏障是授权转移点：当时保留的有限安全 STOP 归属于已获授权的发布操作，携带不可序列化、不可克隆的一次写出票据凭证。凭证严格绑定原 STOP 的命令、目标、ID、来源类别、run_id、配置／传输代次、原截止时间及屏障的新 control 代次；只有这些已经保留的 STOP 可以继续。原一般来源租约不再阻断这份已接纳的安全清理，其他旧动作仍取消，所有新控制仍被屏障阻挡。不能更换目标、改为开／关等动作、延长时限、跨配置重用，也不能在屏障前借此绕过撤权。发布不会凭空生成此前未排队的电机 STOP。

受信任的本地 `Publisher::publish` 保持原有授权约定；HTTP 激活必须使用绑定证明的发布入口。候选不增加管理员发布配置所需的逐设备权限，也不会自动启用规则。已完成收据继续按现有授权查询规则返回；丢失响应仍保持未知、不自动重试。

凭据变更接口已有 Tokens 锁内重鉴权，不能与上述发布队列缺口混为同一失败结论。备份、其余管理变更、HAP 全入口和现场长时间运行也不能据本候选宣称完成验证。未知窗帘参数和待确认原系统条件继续挂起，不自动启用规则。

## 组合灯部分写出

普通 HTTP 组合灯按既有顺序先写调光目标、再接通隐藏供电；五种来源情况已在第一帧 Written 后检查第二帧，已写出的帧不撤销、不重放，未发送的后续帧受精确来源约束。没有为此改变帧顺序，也不扩大 hidden supply 的显式权限。

原生相对场景在供电状态未知时使用另一条真实链路：先对隐藏供电 Toggle，查询并取得更新的供电反馈后，才发送条件调光。五种情况已在供电及其查询 Written、调光尚未接纳时检查来源变更，失权后的调光为零；不撤权时目标调光正常写出。两条链路均核对另一合法来源返回的 command_id 自身 Written。
