## 1 目标与功能边界

第一阶段交付完全在局域网运行的中控：支持物理面板操作、Apple「家庭」App 与 Siri 控制、浏览器维护、灯光开关与调光、窗帘升降停止、场景执行、条件与变量、运行诊断及备份恢复。互联网断开时，现场控制应继续工作。

系统保留可用的现有 TCP485 网关和 RS485 总线。Rust 服务主动连接网关，将逻辑设备命令转换成 HopeBeauty 报文，并将反馈转换成可供界面和规则使用的事件。

## 3 核心架构

系统采用一个 Rust 常驻进程，内置原生 HomeKit HAP over IP 服务，并提供静态 Web 管理前端。Apple 家庭 App 是日常控制入口；HAP 接入模块直接调用中控的类型化命令入口并订阅状态，不经过独立桥接进程或本机 HTTP 转发。每条物理总线由一个独占的网关任务维护连接和发送队列；HAP、Web、场景和规则使用同一套命令仲裁，避免不同来源绕过仲裁直接写总线。

```mermaid
flowchart TD
    Panel["墙面面板"] --> Bus["HopeBeauty RS485 总线"]
    Modules["开关 调光 电机模块"] <--> Bus
    Bus <--> Bridge["TCP485 网关"]
    Bridge <--> Driver["连接管理 帧解析 发送仲裁"]
    Driver <--> State["设备模型 状态与事件"]
    State <--> Engine["场景引擎 规则引擎 变量"]
    API["HTTP API 与事件订阅"] <--> State
    API <--> Engine
    UI["Web 管理界面"] <--> API
    Apple["Apple 家庭 App 与 Siri"] <--> HAP["Rust 原生 HAP 配对 加密 配件服务"]
    HAP <--> State
    HAP <--> Engine
    DB["SQLite 配置 变量 审计"] <--> State
    DB <--> Engine
    Import["Control4 项目导入器"] --> DB
```

网关任务拥有 TCP socket。其他模块通过有界消息通道提交命令；接收反馈形成统一事件。状态修改由集中状态任务排序，规则读取事件对应的状态版本。数据库写入通过独立任务批处理，不阻塞按键接收和 STOP 命令。

部署只保留一个有写权限的中控实例。待机或观察实例禁止执行规则与发送控制命令。网关可能允许多个 TCP 连接，这并不提供控制权仲裁；切换期间要在服务和网络层共同保证单一控制者。

## 5 设备模型与地址

为每个房间、逻辑设备、场景和规则分配稳定的内部 ID。Control4 对象 ID、驱动 ID 和 HopeBeauty 地址作为来源映射保留，不作为可变名称。代理对象与驱动对象通过连接关系合并到同一逻辑设备，防止场景引用代理而控制不到实际通道。

设备地址由 gateway_id、十六进制 bus_id 和 channel 组成。面板包含按钮子对象，模块地址在同一物理总线上必须唯一；开关和调光同一模块的不同通道允许共享地址。不同总线可以使用相同地址。

能力字段至少包含 switch、level、motor、button_events、led、state_query 和 feedback。类型与通道上限来自经过确认的型号。项目中调光地址 11 至 15 均映射了 8 路，不能按 4 路 GT-E4 配置。面板项目含 Rocker 类型，不能仅凭 BT-86 手册把所有面板固定为 6 键。

### 面板协议配置与现场验证

协议配置（protocol_profile）定义型号支持的通道、命令和值域；现场验证（model_verification）记录该地址的实物是否匹配该配置。二者必须同时满足才能产生控制帧或自动化按键事件。键数是协议配置推导出的能力，不接受调用者传入任意 1–16 的整数来授权报文。界面选择公开哪些按键可以是子集，但不能据此扩展协议范围。

| 面板协议配置 | 已知范围 | 启用条件与处理 |
| --- | --- | --- |
| bt86c_rs485_v2_9_6_2 | 按键 1–6，反馈 D1–D6 与 F1/F2；LED 通道 01–06 | 实物型号、地址与布局核对后开放按键事件；LED 另需确认手动模式 |
| 未确认型号或 Rocker 布局 | 不推断键数或命令映射 | 保存原始项目字段及报文，标记 pending；不生成控制帧或按键事件 |
| 后续新增型号 | 由独立协议配置显式列举 | 补齐协议依据、固定测试向量与现场验证后启用，不自动继承 BT-86 编码 |

现场验证记录至少保存协议配置 ID／版本、实物型号、地址与布局核对结果、依据和验证时间。面板 LED 模式单独记录为 unknown、self_reset 或 manual；只有 manual 才开放 led 写能力。允许按键反馈不等于允许 LED 控制，不在常规 API 中修改 C8 模式。型号、地址或协议配置变更使相关验证失效；LED 模式被修改或设备恢复出厂后重新核对。

草稿可以保留 pending 设备用于迁移诊断，发布时这些设备保持禁用，依赖其动作或事件的规则标为 disabled_pending。原始接收层仍可记录它们的 RawFrame，语义分类层返回未验证／不支持原因。已确认 BT-86 的 D7–E0 等未定义反馈保留为未知帧，不能触发按键规则。模拟器可显式选择已知协议配置测试，但模拟验证不能改变现场验证状态。

```json
{
  "schema_version": 1,
  "device_id": "light-basement-corridor-15-1",
  "name": "过道15-1",
  "room_id": "basement-leisure",
```

## 6 HopeBeauty 协议与驱动

普通控制帧为 5 个原始字节：AE ID CMD VALUE EE。文档中的十六进制表示法不是 ASCII 文本。串口参数为 9600 baud、8 数据位、无奇偶校验、1 停止位；这类普通帧没有文档定义的校验和。ID=00 是广播，常规 API 禁止使用。

以下 c 表示通道；A0+c、B0+c、D0+c 表示字节加法，亮度为十进制 0 至 100 的字节值。

| 类型 | 动作 | CMD | VALUE |
| --- | --- | --- | --- |
| GT-C8 开关 | 开／关 | c | F1／F2 |
| GT-C8 开关 | 查询 | A0+c | F2 |
| GT-C8 开关 | 状态反馈 | D0+c | F1／F2 |
| 调光模块 | 立即设置 | c | level |
| 调光模块 | 模块渐变 | B0+c | level |
| 调光模块 | 查询 | A0+c | F2 |
| 调光模块 | 亮度反馈 | D0+c | level |
| 调光模块 | 暂停渐变 | A0+c | 05 |
| GT-M4 电机 | 升／降／停 | c | F1／F2／F0 |
| BT-86 面板 | 按下／松开反馈 | D0+c | F1／F2 |
| BT-86 面板 | LED 开／关 | c | F1／F2 |

例如地址 15 的第 1 路调光设为 30%，发送 AE 15 01 1E EE；地址 05 的第 2 路开关关闭，发送 AE 05 02 F2 EE。

反馈按地址对应的设备类型解释。AE ID D1 F1 EE 对开关是开状态，对面板是第 1 键按下。未知地址不能自行推断为开关或触发规则。GT-M4 手册只定义动作，不提供百分比位置反馈。面板 LED 接受命令依赖其手动模式，切换模式和其他模块参数不在普通操作接口中开放。

TCP 输入使用累积缓冲区处理任意分包和粘包，寻找 AE 后按固定 5 字节验证 EE；错误候选逐字节重新同步，并限制缓冲区大小。数据字节可能为 AE 或 EE，不能遇到 EE 就截断。语法合法但类型或值未知的帧进入诊断日志，不产生自动化事件。

CC 固件查询返回 ASCII，与普通帧格式不同。首期驱动不在状态轮询中使用该命令；后续支持时设专用维护模式和独立解析策略。未知帧和短路噪声不能被当作设备状态。

## 7 网关连接与命令可靠性

连接状态依次为 Disconnected、Connecting、Synchronizing、Ready；连续失败进入 Degraded。连接成功后先恢复帧接收，再分批查询可查询设备，最后开放依赖状态的自动化。重连采用指数退避和随机抖动，初始设计上限 30 秒。

发送队列优先级为 STOP、人工即时控制、按键规则、场景、后台查询。优先级只能重排尚未写入 socket 的命令，不能撤回网关已缓存的字节。同一设备的动作保持约束顺序；窗帘换向的 STOP 与后续动作作为受约束序列执行。

队列必须有容量上限、过期时间和来源标识。调光滑块产生的连续立即设置可以合并为最新值；STOP、按键事件、变量操作和规则节点不能任意合并。取消场景删除其尚未发送的动作，后续迟到反馈仍用于更新真实状态。

5 字节在 9600 baud、8N1 下理论串口占用约 5.2 毫秒，不含网关与设备延迟。初始发送间隔为 20 毫秒，属于保守调试值，不是厂家要求；当前 TransportOwner 已以固定默认值实施，查询与控制共用写出间隔，等待后才出队，配置化尚待完成；根据现场丢帧和响应数据调整。该设置下 96 条命令至少需要约 1.92 秒，不能要求全屋 96 路同时完成。

协议没有请求序号和通用 ACK。执行状态必须区分 queued、written、observed、timed_out、cancelled、failed。written 只说明本地写入传输层，不证明负载动作完成；灯光通过同地址同通道反馈进行状态核验，仍不能证明反馈只来自本次命令。LED 和电机没有已确认的通用执行 ACK，只记录已发送与验证能力。

确定目标值的灯光操作可在查询后有限重试；TOGGLE 等相对操作、电机动作和规则整体禁止自动重放。网络中断后清空过期控制队列，不在重连时突然执行旧场景。使用绝对开关目标代替硬件 toggle，可以减少不确定重试。

后台查询合并相同通道请求，限制并发，避免多个任务对同一反馈等待。默认每个通道设置可调查询超时，首轮按 1 秒调试；场景拥塞时延后查询，连续失败降低频率。主动反馈、全模块查询、回包顺序和多连接行为均须现场验证后启用。

## 8 状态一致性与断电恢复

每个可控属性保存 desired、observed、quality、source、observed_at、version 和 pending_command。quality 至少包括 unknown、confirmed、stale、estimated。UI 优先展示 observed；发送命令后可以展示等待提示，但不能立刻标记 confirmed。

灯光状态以有效反馈确认。反馈来自现场面板或其他本地联动时也更新状态。重复的相同值反馈更新观测时间，不重复产生状态变化事件，避免轮询触发规则循环。

窗帘保存 last_command 和动作时间。未安装位置传感器时，真实 position=null；如果用户完成行程校准，可另外显示 estimated_position，并明确标记估算。重启、掉电、通信故障或现场手动干预后估算失效。首期 UI 使用开、关、停按钮，方向通过校准映射。

逐通道配置 `motor_calibration` 保存 `open_direction`（`up` 或 `down`，指协议电气方向）、`stop_verified`、`evidence` 与 `verified_at_unix_ms`。该记录与模块型号验证分开；只有方向和 STOP 均已现场确认才填写。配置层将 `MotorAction::Open/Close/Stop` 转换为电气 `MotorMotion`，缺失校准或设备禁用时拒绝生成日常控制命令；校准不会自动启用设备或提升模块验证状态。维护联调的原始报文路径不等同于日常控制入口。`Admission::submit_motor` 在命令所有者线程中读取持久配置并完成方向映射，复用鉴权、持久接纳、STOP 优先级和传输审计。当前 HAP 配件图仍仅支持灯光，后续窗帘适配器必须调用逻辑命令入口，不能绕过校准直接提交电气升降命令。

运行状态快照用于故障分析，不能在重启后作为已确认现场状态。持久化的场景变量与设备观测分开：逻辑模式可以恢复，物理状态重新查询，条件遇到 unknown 不执行需要确定状态的动作。

恢复流程为加载配置、检查 schema、恢复变量、建立连接、查询灯光、发布状态就绪、开放相应规则。面板断链时取消未完成的长按计时器；连接恢复不能补发“曾经按下”的动作。

## 9 场景引擎

每个场景包含稳定 ID、成员动作、延迟、目标亮度、渐变时长、执行顺序、失败策略和冲突策略。导入同时保留原始 track_level、delay、rate、level 字段；这些字段的具体语义必须结合驱动与原系统行为校验，不能仅凭名字直接对应。

所有延迟相对单调时钟的场景开始时间计算。相同到期时间保留源配置顺序，经总线队列逐条发送。场景是有时序的动作集合，RS485 协议不提供跨设备事务；部分成员失败时报告 partial，首期不自动反向补偿已成功动作。

立即控制、模块自身渐变和软件渐变作为三种能力区分。模块的 Bx 命令使用其内部渐变设置；原项目的 Ramp Timer 与场景 rate 不能直接放进报文。需要精确时长时，可通过软件定时输出分段亮度，但必须计算总线预算、合并采样并接受实际完成误差。首期优先采用经验证的模块渐变，再覆盖有明确时长要求的少量场景。

人工控制默认取消该设备在当前场景中的剩余动作，其他设备继续；新场景覆盖同一设备的旧目标，记录冲突原因。STOP 始终优先。调光模块自身正在渐变时，新目标或取消操作是否应先发送暂停命令由实测行为确定。

场景 active 由成员目标与可观测状态的匹配结果计算；同时保留 last_run 和 run_status。缺少反馈、仍在渐变或成员失败时显示 pending 或 unknown，不能只因命令已发就显示场景已达成。DEACTIVATE_SCENE 的原始语义要在导入时查明，不能统一转换成全部关灯。

原项目“卧室-全开”包含两路开关全开和两路调光到 14%，调光元素的 rate 为 1000。名称不等于所有成员都到 100%；转换保留实际元素，并将 1000 的单位和执行行为列为对照测试项。

## 10 事件规则与面板操作

规则结构包含 trigger、condition AST、actions、变量读写、启用状态、执行预算和来源节点。采用类型化语法树，保留嵌套层级、顺序和 Else 分支，不将原程序压平成命令列表。

主要事件包括按键按下、松开、单击、双击、长按开始、长按释放、灯光状态变化、变量变化、场景执行结果、启动同步完成和计划任务。手势时间使用单调时钟，时区只用于日历计划。

首期手势参数设为可配置值：重复边沿抑制 30 毫秒、长按阈值 600 毫秒、双击窗口 300 毫秒，均为待调试值。产生双击时是否同时产生单击由按键配置确定；存在双击动作的按键默认延后单击，不能先执行单击后再无条件执行双击。按下即执行与单击执行分别建模。

长按调光每个面板和通道只允许一个活动任务，松开立即取消。丢失松开时通过最长运行时间中止，初始上限 10 秒；总线断链同样取消。摇杆面板需要明确上、下键及方向，不通过未经确认的键号猜测。

规则执行时先读取一致的状态版本，变量修改按序处理。不同规则对同一设备的输出由命令仲裁决定。规则链保留 correlation_id 和 causation_id，检测重复路径并限制深度、动作数与运行时间；超预算停止该链并记录诊断，不使整个中控崩溃。

25 个项目变量分为逻辑模式、临时执行状态和设备状态缓存。逻辑模式可持久化；临时执行状态重启清空；缓存状态以反馈刷新。条件求值采用 true、false、unknown 三值逻辑。遇到 unknown 时跳过该条件的整个分支并记录诊断，不执行 Then 或 Else，也不把 unknown 当作 false 或亮度 0；只有显式检测未知状态的规则可以处理该情形。

面板 LED 可绑定场景状态、模式变量或设备状态。原项目显式 LED 动作优先保留，统一状态绑定仅在确认行为一致后替代。面板模式、背光与模块主动反馈参数放入维护配置，不在规则中自动改写。

## 11 Control4 项目迁移

导入流程为归档检查、XML 与驱动描述解析、对象和连接映射、设备规范化、场景转换、事件转换、引用检查、覆盖报告、模拟回放、生成待发布版本。导入器不执行压缩包中的 Lua，不绕过加密驱动授权；控制能力依据公开厂家协议重新实现。

读取归档限制文件数、解压后大小和 XML 深度，拒绝路径穿越；忽略未需要的二进制内容，XML 禁用外部实体。授权密钥、账号和令牌不进入规范化配置、日志或导出报告。

命令分发必须同时检查设备类型和命令参数。例如 Turn On/Turn Off 在面板对象上可能控制 LED，在灯光对象上则控制负载，不能按命令名称统一处理。SET_LEVEL、SET_LEVEL_TARGET、RAMP_TO_LEVEL、STOP、ACTIVATE_SCENE 与变量更新分别建立转换器。

导入产物至少包括 devices、rooms、scenes、rules、variables、source_map、unsupported_nodes 和 validation_report。每个转换结果追踪到原始对象、事件和节点，便于回查。未支持节点导致对应规则处于 disabled_pending，而不是静默丢弃后启用。

覆盖报告按原始对象和语法节点统计 converted、needs_review、unsupported、invalid；保留原始统计口径，不能把“解析出 2170 个命令”表述为“2170 个命令已经兼容”。计划任务也应检查：当前提取的 4 项主要是系统代理更新，不能当作家庭照明任务直接迁移。

对照回放使用原项目事件树和已确认的预期结果建立样例。至少覆盖每个房间的常用面板、全开全关、重复按键、窗帘停、场景覆盖、变量分支及 LED 同步。没有原驱动执行语义的节点须用现场行为或人工确认补齐。

## 12 配置和数据存储

配置分为静态设备定义、自动化定义和运行参数。SQLite 保存经过验证的配置版本、活动版本指针、变量、迁移映射、场景运行记录和操作审计；TOML 保存服务启动、网络监听和存储路径。敏感凭据使用独立受限文件或系统凭据机制。

自动化文档可声明 `variable_migrations`，每项包含 `variable`、`source_revision`、`source_type`、`conversion` 和非空 `review_evidence`。目标必须是当前文档声明的持久变量，源必须存在且属于预期活动版本。转换支持 `bool_to_integer`（false/true→0/1）、`integer_zero_one_to_bool`（仅 0/1 可转换）及 `reset_unknown`（显式丢弃原值）；未知源值保持未知。省略声明时，同名同类型保留，类型冲突拒绝。发布前校验源状态，事务内再次读取并转换，与设备／规则文档及活动版本一起提交；任一失败全部回滚。旧版本值保留用于审计，启动只读取已发布结果，不重放迁移。后续版本应删除已执行声明或提供新的准确源版本，旧声明不能重复套用。此机制不把临时值或反馈缓存迁为持久值，也不推断原项目变量用途。


配置编辑在 draft 版本中进行。发布先完成类型、范围、地址唯一性、引用、规则预算和总线容量检查，再按第 25 节的发布屏障和事务切换活动版本。首期每次成功发布统一结束所有旧 revision 的活动场景及规则任务，取消其延迟定时器和未发送普通动作；不支持旧场景跨版本继续执行。即使只修改名称也遵循同一规则，发布界面提前列出将中止的运行。名称或规则修改可在进程内完成，网关地址和总线结构修改还需要维护流程重建连接。

数据库采用单写入任务、事务和 schema 迁移。备份使用 SQLite 一致性备份机制；不能直接复制正在使用的数据库主文件而遗漏 WAL。建议每日备份及每次配置发布前备份，保留策略可配置，初始保留最近 30 日和最近 20 个发布版本。

审计默认保留 30 日。原始总线报文日志只在诊断模式启用，并限制文件大小和保留时间，避免闪存持续写入。崩溃后数据库恢复不能回放历史动作。

## 13 API 和权限

所有控制来源使用统一 API 语义。浏览器界面与外部适配器不得直接访问 TCP485。HTTP 写请求具备鉴权、权限、参数校验、request_id、幂等键及结果查询。

| 接口 | 用途 |
| --- | --- |
| GET /api/v1/rooms | 房间和楼层 |
| GET /api/v1/devices | 定义、能力及状态 |
| POST /api/v1/devices/{id}/commands | 开关、亮度、电机或 LED 操作 |
| POST /api/v1/scenes/{id}/runs | 启动场景 |
| POST /api/v1/runs/{id}/cancel | 取消剩余动作 |
| GET /api/v1/runs/{id} | 执行结果与失败成员 |
| GET /api/v1/diagnostics | 网关、队列、同步与错误 |
| GET /api/v1/config/versions | 管理员查看配置版本 |
| POST /api/v1/config/versions/{id}/activate | 验证后发布 |
| GET /api/v1/events | 经鉴权的 WebSocket 订阅 |
| GET /health/live 与 /health/ready | 进程存活与设备服务就绪 |

控制请求通常返回 202 和 command_id，只表示已接收。队列满返回 429 或 503；值越界返回 422；设备未具备能力返回明确错误；网关离线的普通动作默认拒绝，不积压到恢复时执行。

```json
{
  "request_id": "client-request-001",
  "action": "set_level",
  "level": 30,
  "transition_ms": 1000,
  "expires_in_ms": 2000
}
```

transition_ms 只在设备或软件渐变能力已启用时接受；不支持则明确拒绝，不能忽略。重复的幂等键必须返回同一执行记录；相同键配不同内容返回冲突。窗口大小与过期策略配置化，进程重启后的重复请求也不能无条件执行相对动作。

事件带递增序号、状态版本、事件类型和来源。订阅客户端断线后请求最新快照，若服务不能补齐历史则返回 resync_required，不要求 UI 凭丢失事件继续推断状态。

角色分为家庭成员、访客和管理员。家庭成员操作允许的房间；访客受房间和场景范围限制；管理员配置和诊断。浏览器使用受保护会话、来源检查和 CSRF 防护；外部令牌可撤销并限定范围。首期不开放公网端口；Apple 家庭 App 的远程访问使用其家庭中枢机制，Web 管理远程访问使用受控 VPN。Apple 家庭权限与 Rust API 权限分别管理，原生 HAP 会话只允许操作已公开设备和场景，不暴露配置发布接口。HAP 配对控制器标识用于会话鉴权和审计，不能直接等同于某位 Apple 家庭成员。

## 14 Apple 家庭 App 与管理界面

Apple 家庭 App 按房间组织日常控制，在配对后由用户确认房间归属；Web 管理界面按地下室、第一层、第二层和房间组织，提供常用场景、当前灯光状态与快捷全关。Web 房间页显示开关、亮度滑块、窗帘开关停和可用场景；滑块交互在客户端与服务端共同限制频率。

控制后显示等待、已观测或失败，未知与离线状态清楚可见。窗帘只显示经过校准的开、关、停和动作记录；位置估算如启用，必须带估算标记。场景执行页列出失败成员，让用户能够知道哪些负载没有确认响应。

实体面板与 Apple 家庭 App 共同承担日常操作；Web 界面用于配置、校准、迁移和诊断。诊断页只向管理员显示总线地址、反馈时间、队列长度、重连次数、规则链和迁移异常。普通用户界面不暴露十六进制命令、配置版本或数据库字段。

前端静态资源与后端同源提供，避免首期额外跨域认证。兼顾手机竖屏、平板和桌面，断网时保留本地资源；所谓离线运行仍依赖家庭局域网和中控服务可达。

## 15 部署与网络

候选宿主为 nanopc，采用原生 Linux systemd 服务。若其继续承担家庭路由，控制服务必须使用独立账户、资源限制和独立数据目录；中控升级不得修改 PPPoE、rproxy、rdhcpd、OSPF 或现有路由配置。路由与中控共享宿主会增加共同故障风险，可在稳定后迁移到独立设备而保持配置兼容。 原生 HAP 与中控一起运行，无需部署独立 Node.js 服务；HAP 监听器、Web API 和 HopeBeauty 连接分别绑定明确的接口与端口，资源预算包含加密会话及事件订阅。

建议部署目录：/usr/local/bin/homesensed、/etc/homesense、/var/lib/homesense 和 /var/log/homesense。运行账户 homesense 不拥有网络管理权限，不以 root 常驻；TCP485 接入不要求串口特权。日志优先交给 journald。

`homesensed.service` 的 systemd 配置采用 Restart=on-failure、启动频率限制、NoNewPrivileges、受限写目录、内存和 CPU 预算；具体沙箱选项在目标系统验证。接收 SIGTERM 后停止接单、取消尚未发送动作、保存变量并关闭连接；不能把“进程退出发送 STOP”当作窗帘安全保证，因为链路可能已经断开。

监听优先绑定管理 LAN 地址，避免意外监听 PPPoE/WAN。允许家庭管理网访问 API，仅允许中控连接网关 50007；远程管理通过经过授权的现有管理通道。网关位于 192.168.0.10 时，应验证路由、返回路径及网关默认路由。

时间使用系统时钟同步，日历任务按 Asia/Shanghai 运行；动作延迟和手势使用单调时钟，NTP 跳变不能延长窗帘动作或重复执行场景。局域网 DNS 名称在部署时确定，不在设计阶段修改现有记录。

## 16 可用性与故障处理

| 故障 | 系统行为 | 恢复条件 |
| --- | --- | --- |
| TCP 网关离线 | 标记状态 stale，拒绝普通新动作，取消过期队列 | 重连并重新同步 |
| 反馈缺失 | 执行超时，保留未知或旧观测，不伪造成功 | 查询或人工核对 |
| 单个规则异常 | 停止该规则链并记录来源 | 修复配置后重新启用 |
| 队列拥塞 | 低优先级查询退让，保留 STOP 容量 | 流量回落或定位循环 |
| 数据库写失败 | 标记 storage_degraded，暂停自动化及普通写入；仅按下述白名单允许已启用的手动降级 | 存储验证与设备状态同步完成后恢复 |
| 磁盘不足 | 停止诊断报文留存，清理可轮转日志 | 释放空间后恢复 |
| 服务崩溃或重启 | 不回放旧动作，重新查询状态 | 同步完成后开放规则 |
| 宿主断电 | 使用模块既有硬件行为，恢复后重同步 | 宿主与网关恢复供电 |

### 数据库故障下的控制入口

manual_degraded_enabled 默认 false，只有管理员在存储正常时明确启用并持久保存后，当前进程才能进入有限手动降级。前提是内存中仍有最后一次有效配置、现场验证结果和既有授权，且对应网关 Ready、当前进程仍持有控制权。冷启动无法加载这些资料时不开放降级写入。运行中禁止通过降级入口改变配置、身份或权限。

| 入口 | storage_degraded 时的行为 |
| --- | --- |
| HTTP 控制／场景／配置写接口，包括 Web 控制 | 一律返回 503 与 persistence_unavailable，不入队；不以易失幂等记录替代持久化承诺 |
| HTTP／HAP 状态读取 | 可返回授权范围内的内存观测，保留原 quality／时间；Web 明示存储降级，读取不触发控制 |
| 已配对 HAP 会话的直接设备写入 | 仅在降级开关已启用时，接受白名单动作；否则返回适配器定义的明确失败 |
| 已验证物理面板的直接手动绑定 | 仅执行预先配置的白名单动作；不运行一般规则树、场景或手势自动重复任务 |
| 场景、计划任务、普通规则、变量更新、HAP 场景入口 | 停用并拒绝新执行 |
| 配对、撤销配对、身份和权限变更 | 不确认需要持久化的变更成功；恢复存储后重试 |

白名单限于已验证灯光的绝对开／关、立即亮度设置，以及已验证电机的 STOP。面板翻转、长按渐变、电机升降、LED、模块参数和其他相对动作均不在白名单。HAP On 写入先按已确认亮度／配置默认值归一化为绝对目标，禁止在此模式自动选择模块渐变；归一化所需信息不足则拒绝。普通规则树不得伪装成“面板手动绑定”进入该路径。

降级动作仍经同一鉴权、能力检查、控制权、deadline 和有界队列仲裁。它们不承诺跨重启幂等，禁止自动重试和恢复后补发；最多只记录有界内存执行结果及尽力日志，向 Web 明示审计未持久化。HAP 的接受仍只表示已入队，confirmed 只能来自有效设备反馈，STOP 也不宣称物理动作已确认。内部只读状态查询可按原配置继续合并限速调度，用于刷新观测和恢复检查，不经过降级动作白名单，也不触发一般规则；HTTP／HAP 读取仍只读内存快照。

检测到存储故障后，阻止新普通动作、增加 control_epoch、停止活动场景／规则及定时器，并取消旧代际的未发送普通命令。已经写入的命令继续接受观测；无法保存其最终执行结果时标明持久化不可用，不虚构持久化成功。待发 STOP 仅在上述手动降级条件满足时，按原始地址快照作为新降级动作重新验证后保留，否则报告未发送。故障期间的运行终止结果若未落盘，重启将历史非终态记录标为 uncertain，不重新执行。

恢复顺序为验证数据库可读写、检查活动 revision 与内存配置一致、重新同步设备状态，再通过仲裁屏障增加 control_epoch 并退出降级；切换时取消未发送的降级动作，STOP 按第 25 节的排空约束处理。revision 不一致则停止降级并进入维护恢复，不能自动混合配置。新普通请求在恢复完成后接受，故障前和故障期间的旧任务都不重放。

现场模块手动按钮、面板本地联动和中控离线后的行为必须逐项实测。不能假定墙面面板在 EA-5 和新中控均离线时仍能控制全部负载。电机安全最终依赖现有互锁和输出时限，软件 STOP 是补充措施。

## 19 切换与回滚

切换分为离线准备、观察模式、测试房间、分区接管、整屋接管和稳定运行。观察模式只接收和记录反馈，禁止执行规则与控制命令；若新增 TCP 连接会改变网关行为，则停止并改用离线回放或受控维护窗口。

数据库升级采用兼容检查和备份；代码回退不得直接打开不兼容的新 schema。升级包与配置版本绑定记录，先验证恢复能力再删除旧版本。

## 23 Apple 家庭 App 接入设计

日常使用 Apple 家庭 App 控制设备和运行常用场景，Siri 作为语音入口。Rust 中控继续负责现场面板、HopeBeauty 驱动、既有规则和精确场景时序；这些能力在 HAP 接入任务或 Apple 家庭中枢不可用时仍应保持运行。Apple 家庭提供的界面能力通过 原生 HomeKit HAP over IP 配件接入，单独提供 HTTP API 不会自动出现在家庭 App。[Apple 开发者说明](https://developer.apple.com/apple-home/)

### 接入路径

首期采用原生 Rust HAP over IP，将中控作为 HomeKit Bridge 提供给 Apple 家庭 App。homesense-hap 模块负责 HAP 配件服务、发现、配对、加密会话、特征读写与事件订阅；Homebridge、Node.js 和自定义桥接插件不再作为部署依赖。hap-rs 是候选开源协议实现，已有 IP 配件服务器、mDNS 和灯光示例；正式采用以实际构建、桥接能力、安全审查和 iPhone 验证通过为准。[hap-rs 源码与说明](https://github.com/ewilken/hap-rs)

HAP 写请求在协议层完成配对身份和写权限校验后，转换成 homesense-core 命令，经中控仲裁后交给 HopeBeauty 驱动或场景引擎。HAP 读取来自统一状态快照，反馈变化通过 HAP 事件通知推送；HAP 接入层不重复计算场景、不直接写总线，也不依赖自定义插件令牌。Web HTTP API 保留给维护和其他适配器。

采用 HAP over IP 保留现有以太网与 RS485，不要求 Thread 网络或新增无线模块。Matter 只作为后续适配方向预留，首期不启用；同一逻辑设备只公开一份 Apple 配件身份，防止多协议接入造成重复控制。

### HAP 服务边界与安全存储

homesense-hap 包含协议库适配、配件模型映射、状态投影、命令转换、会话管理和发现管理。业务层只依赖中控命令与事件类型，HAP 库类型不渗入 HopeBeauty 协议、规则树或存储模型。HAP 无法启动时标记该接入通道 degraded，并保留可正常运行的面板与 Web 控制；任务错误隔离不能消除同一进程崩溃导致的整体中断，仍由 systemd 和重启同步流程恢复。

配对密钥和控制器关系放在专用持久存储，限制到服务账户读写，不进入诊断日志、普通配置导出或 Pages 文档。备份包含身份、权限、配置编号和标识映射，备份副本需加密并限制访问。恢复到新宿主时先停止旧实例，避免两个实例使用相同配件身份同时广播和接受控制。解除最后管理员配对、恢复配对模式和重置后的行为按协议要求专项验证。

监听会话数、未完成配对数、请求大小、握手耗时、订阅数和事件队列均设上限。错误配对与异常请求限速，订阅客户端过慢时断开并要求重读状态，不拖慢总线控制。加密依赖接受版本锁定、已知漏洞检查和畸形输入测试，不把“能够配对”作为安全实现完成的唯一依据。

### 原型实施顺序

先验证一个虚拟调光灯的配对、On/Brightness 写入、主动状态通知和重启后保持配对，再验证一个包含多个灯光配件的桥与撤销配对。随后接入一组真实开关和调光负载，验证面板反馈能同步到家庭 App，最后扩展到多个楼层桥、场景动作入口和经过校准的窗帘操作。候选库未通过验收时先修复或替换 HAP 适配库，保持原生 Rust HAP 的架构决策，不能静默退回独立桥接服务。

| 面板 LED、内部变量 | 默认不公开 | 保留在 Rust 规则和维护界面 |

On=true 对调光灯的含义须明确：初始策略为恢复非零的已确认亮度；没有可恢复值时使用该设备配置的 default_on_level。On=false 设置亮度 0；Brightness 的设置采用可配置交互渐变策略，不擅自覆盖原场景 rate。

虚拟动作开关的关闭或自动复位不发送反向动作。homesense-hap 在中控接受请求后复位；执行失败在日志和 Web 运行记录中显示。家庭 App 的开关状态仅表示触发入口，不承担完整场景进度显示。

不能把 68 个 Rust 场景直接声明为 68 个 Apple 原生场景。桥接公开选定场景的触发开关，用户可在家庭 App 中创建同名场景并将该开关打开。涉及延迟、变量和渐变的场景只在 Rust 执行；简单 Apple 场景可直接操作灯光，但同一场景只能选定一个执行归属。

窗帘没有反馈时，不默认公开需要 CurrentPosition 的原生窗帘服务。用户若接受行程估算，也必须通过 Web 明确启用并了解家庭 App 可能无法突出显示“估算”标记；首期仍使用动作入口。停止操作在真实 iPhone、Siri 和负载上单独验收，不能只因服务声明 HoldPosition 就认为家庭 App 已提供可用停止按钮。

### 配对与设备身份

每个逻辑设备的内部稳定 ID 持久映射到 HAP accessory ID（AID）；每个服务与特征持久映射到 instance ID（IID）。AID 在桥内唯一，IID 在对应配件内唯一；重启、改名、新增设备和配置发布不能重编号，不立即复用已删除对象的标识。HAP 数字身份与内部 UUID 分开管理，原 Homebridge 配件缓存不作为新实现的存储模型。

设备按楼层分组到多个 HAP 桥实例，每个实例拥有独立配对身份、监听端口和配件标识空间，可由同一 Rust 进程运行。配件规模以实际 HAP 实现和 Apple 客户端限制验证，初期只公开常用设备与场景。新增配件在家庭 App 中确认房间归属；Rust 房间模型不自动覆盖 Apple 家庭布局。

首次配对由家庭拥有者扫描 setup URI 对应的二维码或输入配对码；码由协议实现生成，不使用源码示例中的固定 PIN。配件长期身份密钥、控制器公钥与权限、配对关系、桥配置编号和 AID/IID 映射持久保存。配件结构变化按 HAP 要求更新配置编号及发现信息，不能通过重建身份处理日常更新。升级与恢复演练验证配对关系和自动化引用仍有效，明确重置才删除身份与配对。

### 家庭中枢与网络

Apple 官方将 HomePod、HomePod mini 或 Apple TV 作为家庭中枢，用于外出控制、家庭共享和自动化；Matter 配件接入还要求设置家庭中枢。部署前登记已有中枢及系统版本，不把普通 Mac、iPad 或 nanopc 当作 Apple 家庭中枢。[Apple 家庭中枢说明](https://support.apple.com/en-gb/102557)

原生 HAP 服务 与家庭设备首期放在可互通的管理 LAN，绑定明确的 LAN 接口和固定 HAP 端口。使用 mDNS 发现，并验证配对后的 TCP 连通。跨 VLAN 时除单播路由和访问策略外，还需范围受限的 mDNS 反射或转发；不能仅放行 TCP 就认为配件发现已经解决。原生 HAP 服务 接口不得绑定 WAN，配对码和管理界面不向公网开放。

HAP 配对、会话验证和加密封装由经过验证的协议库承担，采用 HAP 要求的安全机制，不使用普通 HTTP token、裸 TCP 或自定义加密替代。未验证会话不能访问配件读写与事件订阅；新增、撤销配对和重置按配对权限管理，普通控制者不能修改配对管理数据。家庭 App 权限与 Web 管理权限独立，HAP 不开放源码导入、网络配置或数据库管理。

### 自动化归属与验证

原有实体面板规则、变量及复杂场景在 Rust 内执行，不依赖 Apple 家庭中枢。Apple 自动化适合用户新增的到家、离家和生态联动；对相同按键或条件不再建立重复动作。双击、长按事件既可保留 Rust 规则，也可选定交给 Apple，但不能两边同时执行同一控制链。

homesense-hap 收到设备反馈后更新特征并通知订阅会话，这条路径不产生新的控制写入，避免反馈与写请求互相循环。HAP GET 不因 App 刷新直接触发总线轮询，查询由 Rust 统一调度。状态 unknown、stale 或网关断链时，按特征语义返回可识别的通信失败，不能用 0 或旧缓存伪装成功。HAP 写入成功表示命令被中控接受，不保证现场已完成；负载状态通过后续反馈确认。

验收覆盖：虚拟调光灯首次配对、错误配对码、加密会话、特征读写和订阅、未授权访问、撤销配对、多客户端、房间分配、96 路灯光与面板反馈、Siri、窗帘停止、场景重复点击、中控重启、HAP 任务故障、家庭中枢断线、跨 VLAN 发现、密钥与标识映射恢复及虚拟开关复位。实际 iPhone 配对、反馈和重启保持配对通过后，才将 HAP 从原型推进到真实负载和全屋。

该路径用于本家庭自用部署。若以后销售或分发 HomeKit 配件，另行处理 Apple MFi 要求；Matter 配件则另行处理相应认证。当前设计不声明已获得 Apple 认证。[Apple 配件开发要求](https://developer.apple.com/apple-home/)


## 24 从设备能力到实现接口

本节将第 4 节模块落实为接口约束。下面的 Rust 类型是接口草案，不是已编译的实现；底层协议和外部库的具体类型在实现阶段确定。

```rust
pub enum DeviceAction {
    SetPower { on: bool },
    SetLevel { percent: u8, transition_ms: Option<u32> },
    Motor { action: MotorAction }, // Open / Close / Stop，方向映射先校准
    SetPanelLed { button: u8, on: bool },
}

pub struct CommandEnvelope {
    pub command_id: CommandId,
    pub device_id: DeviceId,
    pub action: DeviceAction,
    pub origin: CommandOrigin,
    pub correlation_id: CorrelationId,
    pub configuration_revision: u64,
    pub control_epoch: u64,
    pub deadline: std::time::Instant,
}

pub enum CommandDisposition {
    Accepted { command_id: CommandId },
    Rejected { reason: RejectionReason },
}
```

DeviceId、CommandId、CorrelationId 使用不同的新类型，避免字符串混用。百分比进入协议层之前验证 0..=100；调用者不能构造任意地址、广播帧或参数修改命令。传输层只接受经过能力检查、地址映射和仲裁的 PreparedFrame。配置中的 bus_id 转换成受校验的 BusAddress，不能在业务层反复解析字符串。

控制入口接受意图，返回 Accepted 或明确拒绝。支持的拒绝原因至少有 unknown_device、unsupported_action、invalid_value、gateway_not_ready、not_controller、configuration_changed、expired、queue_full 和 persistence_unavailable。HTTP 与 HAP 对这些错误分别映射，不把所有错误变成超时。

每个设备绑定一个 driver_id，驱动持有能力集合与传输依赖。HopeBeauty 驱动实现确定目标值、查询、反馈解码；米家适配器只有通过独立验证后才注册相应能力。新驱动不绕过统一状态与仲裁入口。设备地址与 HAP AID/IID 都由稳定内部 ID 映射，名称修改不会改变设备身份。

读状态与查询现场是两个接口：read_snapshot 不产生网络流量；request_refresh 由调度器合并并限速。GET、订阅重连和 Home 页面刷新只读取快照，不能制造一轮全屋查询。驱动可以提交 ObservedEvent，但不得把本地 TCP 写入直接变成 ObservedEvent。

连接管理按传输／网关分别维护，属性质量按设备属性分别维护。某个温度传感器没有电，只把该属性或子设备标为 stale，不把整个网关、其他传感器和 HopeBeauty 总线判为离线。transport_reachable、authenticated、accessory_reachable 和 attribute_fresh 四种状态独立呈现。

## 25 命令、反馈和发布的具体执行顺序

### 一次调光操作

```mermaid
sequenceDiagram
    participant Home as Apple 家庭
    participant HAP as homesense-hap
    participant Arbiter as 控制入口与仲裁
    participant HB as hb-transport
    participant State as homesense-state
    Home->>HAP: 写 Brightness=30
    HAP->>Arbiter: SetLevel，设备ID与截止时间
    Arbiter->>Arbiter: 权限、能力、控制权与容量检查
    Arbiter-->>HAP: Accepted(command_id)
    HAP-->>Home: 按协议返回请求接受结果
    Arbiter->>HB: 排队 AE ID CH 1E EE
    HB->>HB: 写 socket，记录 written
    HB->>State: 收到有效亮度反馈
    State->>State: 更新 observed 与 version
    State-->>HAP: 状态变化通知
    HAP-->>Home: 订阅事件 Brightness=30
```

接受成功之后，HAP 内部的特征缓存不能永久停留在未经反馈确认的新值。on_update 回调是否会使候选库自动更新缓存、如何恢复 observed、如何投影通信错误，列入阶段 A 的必测项；实现不得用短暂回调演示代替真实负载状态一致性。

同一 HAP 写请求可能同时包含 On 和 Brightness。适配器须保留请求内的分组关系并规范化为设备意图：On=false 明确关灯；Brightness=0 明确关灯；On=true 且 Brightness>0 以该亮度开灯。矛盾组合在原型中验证并规定统一拒绝或规范化行为，不能依赖哈希遍历顺序。只写 On=true 时使用第 23 节的恢复亮度策略。跨请求的调光更新可以合并，同一请求的语义不能被合并破坏。

### 超时与不确定执行

控制任务同时保存 transport_epoch 和 configuration_revision。网关断开增加 transport_epoch；排队动作不得跨越该代际继续执行。配置发布增加 configuration_revision，旧映射的动作不按新地址重解释。模式由 observer 切换成 controller 时增加 control_epoch，切换前接收的动作不获得新的写权限。

written 后进程崩溃或网络断开，记录 uncertain，而非 failed 或 confirmed。协议无请求序号，不能保证物理动作 exactly-once。灯光绝对目标可先查询再按策略重试；电机动作、瞬时场景入口与变量更新不得无条件重放。反馈与命令时间相近仅形成状态一致的证据，不证明反馈只属于该命令。

设备反馈无来源字段，不能可靠区分墙面面板联动与某次软件写入。origin 用于记录控制意图，observed 的 source 记录驱动反馈；不把二者强行合并。重复反馈刷新 freshness，但只在值或质量变化时产生规则变化事件。

### 发布与幂等的崩溃边界

配置以不可变 revision 保存。首期采用全局发布屏障，所有发布都结束旧版本的活动任务，不提供“旧场景继续运行”的可选策略。发布按以下顺序执行：

1. 完成 schema、引用、地址冲突、协议配置、现场验证及规则预算检查；列出会被中止的场景和规则。校验失败不触及当前运行任务。
2. 仲裁器关闭新控制请求入口并增加 control_epoch，暂停规则事件分发和后台查询出队，取消活动场景／规则的延迟、软件渐变及手势定时器；已产生但未发送的普通动作、查询和原始事件不跨屏障保留。异步任务带旧 revision 或旧 control_epoch 的迟到结果统一拒绝，不因定时器取消竞争而重新入队；即使发布失败而 revision 未变，旧任务也因 control_epoch 失效而不能恢复。
3. 等待正在进行的单帧写入结束，以便准确区分未发送、written 和 uncertain。待发 STOP 是唯一排空例外：由仲裁器显式接管，重新验证其既有授权、原配置、控制权及有效期，换用当前 control_epoch 并以原地址快照优先写出，不能套用新映射；它不是旧异步任务继续运行。无法完成 STOP 写入、无法确认写入边界或已进入存储降级时，本次发布失败；不声称电机已停止，不用新地址重发。屏障期间的新控制请求（含 STOP）立即返回 configuration_changed／发布中错误，不静默排队；发布需设有限超时。
4. 保存被取消命令和运行结果，并在数据库事务中提交新 revision 与活动指针。提交成功后，仲裁器安装对应不可变配置，清除旧代际待处理事件、未完成手势和依赖条件快照。进程在事务提交后、内存切换前崩溃时，重启从数据库活动指针加载新配置，不恢复旧任务。
5. 对受影响设备重新建立连接／查询同步，再开放普通控制、规则和新的后台查询。无法同步的设备保持 not_ready，不启用依赖其状态的规则。HAP 结构变化按协议更新配置编号并保持身份映射。取消旧任务不会自动撤销已写入的负载动作或模块内渐变，用户可根据当前观测发起新控制。

场景运行结果与成员命令结果分开：未写出任何动作的运行记为 cancelled；已写出部分动作后被发布中止的运行记为 partial，原因 configuration_changed，并保留 written／observed 成员及取消的成员；无法判定已写部分的完成状态时保留 uncertain 标记。正在运行且不再有可取消成员的场景继续核对已写动作的结果，但不得生成补发、重试或后继动作。只剩反馈观察不属于旧场景继续执行。任何被取消的必需成员都不能计为整场景 succeeded。

发布在进入屏障后失败时，活动 revision 以数据库最终提交结果为准；提交结果不明则保持维护状态并读取活动指针确认。已经取消的场景和定时器不恢复、不补发；若仍是旧 revision 且存储、连接均健康，解除屏障后只接受新的请求，否则保持相应 degraded／not_ready。旧配置保留不等于旧运行恢复。暂未发布的导入结果始终不能被运行任务读取。

HTTP 幂等键作用域为 principal + endpoint + key，保存规范化请求摘要、执行记录和过期时间。相同键相同摘要返回原记录，不同摘要返回冲突。幂等记录在响应 Accepted 之前持久保存；事务失败则不发送命令。storage_degraded 时普通 HTTP 写入始终拒绝，不适用手动降级豁免；第 16 节的有限手动通道仅针对已有授权的 HAP 和物理面板。记录 accepted 但尚未发送时崩溃，重启默认不重新排队，由用户重新发起新动作。记录写入与物理执行无法原子提交，必须公开 uncertain 边界。

订阅快照包含 boot_id、state_version 和 event_sequence。序号在同一 boot_id 内递增；客户端发现 boot_id 改变、序号缺口或缓冲溢出，重新取得快照。观察快照与订阅起点要在状态任务内一致地建立，防止“先取快照再订阅”丢失中间事件。

## 26 米家、Aqara 与空调接入

### 已知现场事实和待验证能力

现场已有三台 Aqara 网关：用户命名的空调网关（ZHWG11LM）、餐厅 M1S 和工作室 M1S（两台 ZHWG15LM）。截至 2026 年 10 月 10 日的本次排查，用户确认三台在 Home 中均恢复正常；随后 AP 关联和服务状态可能变化，不写死成架构前提。温湿度传感器离线的已知原因是电池耗尽，不能把全部子设备离线都归因于网关网络。

“空调网关”是用户名称，不等于已证明它向第三方开放空调控制接口。需要列出实际空调设备型号、上游网关型号、控制链路、可读属性和可写命令。ZHWG11LM 与用户所称“小米中枢网关”是否为同一物理设备也需要确认；本设计不把两个名称直接合并。miIO hello、HomeKit 可发现或网关在线都不能证明具备温度设定、模式切换或红外学习能力。

### 分阶段接入选择

| 接入方式 | Rust 获得的能力 | 当前设计定位 | 前置验证 |
| --- | --- | --- | --- |
| Aqara 保持直接接入 Apple 家庭 | Rust 不直接读取其子设备；Apple 自动化可触发 Rust 场景入口 | 首期沿用，保留现有配对 | 所选传感器／空调确实出现在 Home；明确自动化归属 |
| Rust miIO／MIoT 局域网驱动 | 取决于具体设备支持的本地读写能力 | 后续候选 | 精确 model、合法获得的凭据、属性／动作定义、状态反馈、断网验证 |
| Rust HAP controller 读取现有网关 | 仅访问网关实际公开的 HAP 服务 | 后续单独工程 | 控制器实现、配对授权与迁移方案、完整服务枚举、订阅和恢复验证 |
| 小米云接口 | 取决于账号和设备云能力 | 可选扩展，不支撑首期离线控制 | 账号授权、令牌刷新、地区、接口与服务条款、限流与失效策略 |

homesense-hap 是向 Apple 家庭提供配件的服务端；连接既有 Aqara 配件属于控制器能力，两者不共享“能够配对”的验收结果。hap-rs 的现有说明提供 HAP IP 配件服务端，不能把它直接作为可用的 Aqara 控制器库。[hap-rs 项目说明](https://github.com/ewilken/hap-rs)

既有 Apple 家庭配对凭据不假定可导出或转交 Rust。常见控制器迁移流程可能需要先从 Home 移除再由新控制器配对，并重新桥接回 Home；Home Assistant 的官方流程就是如此。它仅作为迁移风险的参考，不证明所有 HAP 配件只允许一个协议配对身份，也不意味着本项目采用 Home Assistant。[HomeKit Device 官方流程](https://www.home-assistant.io/integrations/homekit_controller/)

首期不为了读取传感器而删除、重置或抢占已经正常工作的三个网关。Rust 核心规则只依赖已实现驱动提供的事件；暂由 Apple 自动化执行的跨生态动作必须标注为 apple_home，并接受家庭中枢不可用时无法执行。Rust 无法通过自身 HAP 服务端读取 Home 内其他配件或枚举用户家庭。

### 空调模型与命令确认

独立 climate 能力模型包含 power、mode、target_temperature、current_temperature，以及仅在设备支持时公开的 fan_mode、swing 和 preset。每项属性记录可读／可写、范围、单位、反馈能力与 freshness。使用厂商原生模式枚举映射到统一类型；不支持的制热或风速不出现在控制界面。

若现有链路实际是红外单向控制，发送后只能记录 command_sent，不能标记空调 confirmed。网关上的温度读数不必等于空调回风温度，传感器来源显式区分。红外组合指令可能同时覆盖模式、温度和风速，须由一个 climate actor 串行构造完整目标状态，不能并发发送互相覆盖的部分指令。

本地控制验证至少覆盖开关、模式、设定温度、读回、米家人工操作后的同步、断网、重启和令牌失效；只发现 miIO 设备不计入驱动验收。python-miio 可作协议和设备适配研究来源，不引入 Python 常驻服务作为原生 Rust 核心部署依赖。[python-miio 源码](https://github.com/rytilahti/python-miio)

## 27 网络诊断进入产品验收

本次真实排查观察到：同一 VLAN、同一 SSID 和 TCP 可连接，仍可能存在 IPv6 组播邻居发现间歇失效；换 AP 或重新连接后表现变化。F10 与 F20 均曾出现不完整回复，不能把一次成功或一次失败写成“某型号 AP 必然故障”的结论。现有三个网关当前可用，组播问题的准确根因没有完成确认。

诊断记录区分以下层级，不用一个“在线”覆盖全部结果：

| 层级 | 检查内容 | 不能据此推断 |
| --- | --- | --- |
| 发现 | 当前 mDNS A、AAAA、SRV、TXT 与接口 | 曾缓存的服务一定仍存在 |
| 寻址 | IPv4 ARP、IPv6 NS/NA，按接口重复采样 | 一次 ping 成功表示组播长期稳定 |
| 传输 | 指定地址和接口的 TCP 连接 | 配对认证或属性读取必然成功 |
| 协议 | 认证会话、特征读取、事件订阅 | 每个桥接子设备都在线 |
| 子设备 | 单个属性反馈、观测时间、设备电池 | 子设备失败表示网关全部离线 |
| 中枢 | 当前活动中枢、直连和经中枢查询的差异 | Mac 直连成功表示 HomePod 路径相同 |

HAP 服务端发布的 A／AAAA 必须与实际监听的地址族一致。原型可先验证明确绑定的 IPv4 LAN 服务；只有完成 IPv6 监听、正确的链路本地 scope、组播发现和实际 Apple 会话验证后才公开相应 IPv6 地址。运行时不能通过任意伪造临时 Bonjour 服务记录掩盖连接故障。

未来 HAP controller 保存配件身份与服务名，解析当前 SRV 端口，候选端点带 interface index 和地址族。连接失败刷新发现并选择其他有效候选，遵循有限超时和退避；链路本地地址不能脱离接口使用。ARP／NDP 缓存存在时的 TCP 成功，不作为邻居发现验收；主动探测数据、缓存读取与协议会话分别记录。

原生中控的诊断服务运行时不要求 root，也不自动发送原始以太网探测、改 VLAN、防火墙或路由；低层维护工具在独立受控诊断流程运行。普通健康检查使用服务连接、认证读写与订阅。HAP 通信错误按认证阶段解释，不把未认证 HTTP 的拒绝状态当成配对损坏，也不自动删除身份。

nanopi5 已通过 DHCP Option 121 下发 192.168.5.1/32 经 192.168.3.253 的管理路由，并保留默认网关 192.168.3.1；这是独立网络配置，不是中控启动时的操作。中控宿主若在 VLAN4，须单独确认其实际网关、回程与允许的目的端口，不能直接套用 VLAN3 的路由结论。

网络验收增加：至少一次重启／重新获取租约后的发现和连接、同网段双接口场景、服务端口变化、邻居缓存自然过期后的重连、单个电池子设备离线，以及 HomePod 路径与直接路径的分别验证。记录地址、接口、时间、连接代际与采样次数，不凭设备名称或一次测试输出归因。

### 书房主灯组合控制的现场补充（2026-10-11）

书房主灯实测依赖 03/4 继电器与 12/4 的 AD8 输出。12/4=0% 时单独开启继电器不亮；原系统将 12/4 调至 100% 后，HomeSense 的继电器关／开能控制实灯。此证据仅确认组合关系和继电器实控，尚未验证 HomeSense 调光写入。

后续组合灯须显式声明两个物理绑定，在 HomeKit 中发布一个灯配件；不能将两个独立写操作伪装成总线原子事务。准入须一次校验两个绑定的型号、验证状态、权限、代际和队列容量。开启先准备非零调光目标，再开启继电器；关闭先关闭继电器，保留最后非零亮度。调光值与 On 同批写入时统一规范化，不能因 JSON 字段顺序改变行为。零亮度按关闭处理，初次没有历史亮度时使用显式配置的恢复值。

真实状态由两路新鲜反馈共同决定：继电器断开或亮度为零时为关闭；任一路反馈失效，不以目标值伪造已确认状态。恢复亮度应持久化且仅从有效的非零亮度更新。本地调光期间的中间反馈不覆盖该记录；组合灯供电关闭后也不更新。HomeKit 的 On 与 Brightness 独立表示：关灯时 On=false，Brightness 保留已确认非零值，读数与事件一致；关灯事件即使亮度未变也重新发送该值，以纠正客户端的零亮度缓存。真实输出是否通电仍由 On 和双路反馈决定，未知／失效时记忆不使特征可读。单独开灯优先使用已保存值，无记录才用默认值；中途关灯保留最后已确认亮度，未完成目标不计作确认。HAP 事件在本地调光待完成时抑制中间值，到达目标或 16 秒期限后推送实际值；超时即使实际未变也重新推送，以纠正客户端乐观显示。未知／断线立即解除抑制并报告不可用；物理快照与显式 HAP 读取仍保留真实反馈。中途写失败记录各物理命令状态并使组合投影失效；重连只查询，不重放开灯动作。必须覆盖第二帧失败、EA-5 外部改值、重启恢复和同批 On/Brightness 的测试，再进行书房现场验收。a15 已实现并部署该组合模型及按配置版本隔离的恢复亮度存储；模拟加密 HTTP、两路部分写入和重启恢复测试已通过，现场调光仍待验收。队列仅合并相邻亮度命令，不能跨越供电继电器动作。
