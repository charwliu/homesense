# 华为核心、QNAP与AC配置操作手册

版本1.5 · 2026-10-24整理。当前接线、VLAN与状态统一以[网络架构](network-architecture.md)第1–3节为准。本文记录已验收配置；后续操作必须先匹配实际设备和当前配置，不重放已完成迁移。

## 1 当前维护基线

- 新核心已承担现用VLAN2／3／4／5／100三层服务，不能重新启用旧核心同地址网关。VLAN1尚未按目标接管，隔离维护口VLAN4092不能被误当作业务VLAN1。
- NanoPi5 LAN为Tagged3，直连核心23号；nanopc LAN为Tagged4，直连24号。两口分别使用隔离PVID4090／4091并关闭PoE，不能照搬Access模板。
- QNAP A／B的10号Combo光口接X1／X2；最近核心允许列表分别为2／3／100和2／4／100，隔离PVID分别4093／4094。旧聚合和两核心临时互联不恢复。
- AC LAN直连2号Access5；AP为15 F00、16 F21、17 F12、18 F01、19 F10、20 F20、21 F02、22 F11。15–22均为PVID5，当前允许2／3／4／5／100；业务SSID和客户端结果须另核对。
- 现用485网关`.0.10`经QNAP A上联X1，`.0.11`经QNAP B上联X2；HomeSense仍连接`.0.10:8443`，不要把历史目标`.1.10:50007`写入当前服务。
- VLAN100仍有业务依赖，保留`.0.253`和现有DHCP。NAS、桌面交换机及PE11迁址均不因文档更新而视为完成。

2026-10-24已完成AC100接管和核心VLAN5 DHCP启用并保存：Vlanif5使用全局池`vlan5_ap`，网关`.5.253`；AC100为`.5.1/24`、网关`.5.253`，关闭自身DHCPv4／DHCPv6及SLAAC分配。旧AC已断开。VLAN5网段经OSPF发布，Vlanif5为静默接口，不建立管理网邻居。旧版逐分钟接线过程已归为历史，不再与当前操作表混排。

公开仓库只保留审核后的结构及示例。真实设备导出、MAC、全球IPv6前缀、租约、管理员地址例外和凭证在私有运维目录保存；示例地址不能作为下发参数。

## 2 变更前核查

1. 登记设备型号、固件、实际接口和当前对端，保存运行配置、启动配置及回退入口。完整导出只存私有目录。
2. 确认没有重复网关、重复DHCP／RA或二层环路。旧核心已退出的接口和临时线不能为方便管理而随手恢复。
3. 核对本次授权范围，只修改需要的设备和接口，不连带更改服务器、HomeSense总线、SSID或其他VLAN。
4. 从独立维护入口确认可登录。QNAP仍保留原有6号口本地维护路径；管理CPU是否支持迁到VLAN5尚无完整验证，不修改其管理地址来试错。
5. 停止条件：管理失联、MAC抖动、错误计数持续增长、DHCP／RA来源不符、路由／隔离不符时停止后续步骤，按本次备份回退。

可使用下列只读命令按实机帮助核对；接口名使用实际的MultiGE／10GE名称：

```text
display version
display interface brief
display current-configuration
display saved-configuration
display configuration changes
display vlan
display ip routing-table
display ipv6 routing-table
display ospf peer
display ospfv3 peer
```

不把“配置能解析”“硬件应用success”“链路Up”“真实客户端可达”混作同一个完成条件。

## 3 核心端口、QNAP与AP核对

### 3.1 边界与隔离PVID

| 核心口 | 模式 | 允许业务标签 | PVID | PoE |
| --- | --- | --- | --- | --- |
| 23，NanoPi5 | Trunk | 3 | 4090 | 关闭 |
| 24，nanopc | Trunk | 4 | 4091 | 关闭 |
| X1，QNAP A | Trunk | 2／3／100 | 4093 | 不适用 |
| X2，QNAP B | Trunk | 2／4／100 | 4094 | 不适用 |
| 2，AC | Access | 5，未标记 | 5 | 关闭 |
| 10，现用485网关 | Access | 100，未标记 | 100 | 按实机 |
| 15–22，AP | Trunk | 2／3／100，管理5 | 5 | 按AP实际供电 |

部分Trunk配置会显式保留自身隔离PVID成员；这些VLAN不提供业务三层服务。4092则是已有带管理地址的维护入口，不能按无三层隔离VLAN删除。

### 3.2 QNAP管理与标签

QSW-M408-4C使用QSS的VLAN端口成员设置，T表示Tagged、U表示Untagged。不要仅凭“Trunk”文字忽略每个VLAN的成员和PVID；同一Combo光、电侧不能同时占用。

- 10号口是现用核心上联，不再用于两台QNAP互连。
- 两台原千兆聚合到旧核心的线与旧互联继续按已完成迁移后的状态隔离，不能与新DAC并接形成环路。
- 原6号口本地维护保留；未验证QSS管理CPU标签前，不承诺跨核心管理可达，也不顺手迁管理VLAN。
- NAS原有下游接线保留。新核心X3／X4最近尚无Access3／4配置，不能按旧目标图直接迁线。
- 每次单项保存后重新读回成员、PVID、链路及错误计数，并验证独立维护入口；设备导出不放入公开文档。

### 3.3 AP与SSID

最终名称以F00／F21／F12／F01／F10／F20／F02／F11对应15–22号为准；旧端口description可保留旧名，因此识别时须在私有表核对MAC，不能只看description。

AC管理位于VLAN5。NGR使用VLAN3，NGBOSS使用VLAN2，NGX直接进入VLAN4；维护SSID为单独的VLAN100服务。NGX由nanopc提供地址服务和默认出口，与VLAN4服务器同网段，不套用VLAN2的隔离结论。AP口允许某个标签并不代表该SSID已启用。每块AP分别记录关联、DHCPv4、IPv6地址／默认路由、DNS、公网双栈及隔离结果；此前测试手机的一次10/10不替代所有AP。

维护SSID只选择已登记AP，保持按需启停；不保存真实PSK到仓库。指定AP与本地转发、管理VLAN5和既有业务SSID均须保持独立，不能用AC隧道转发替换原方案。

### 3.4 F01的NGR VLAN映射故障与修复（2026-10-24）

F01为18号口的TL-7AP3622HI-PoE。故障时，新加入NGR的终端取得VLAN5管理网地址；同AP的NGBOSS新加入正常进入VLAN2。从其他AP漫游至F01后可以保留VLAN3地址，因此验收必须关闭再开启终端Wi-Fi，直接在F01新接入，不能用漫游结果代替。

核心18号口对VLAN2和VLAN3均按Tagged放行，PVID为5。AC页面虽已记录NGR绑定VLAN3，故障抓包中目标终端的3个DHCP报文没有802.1Q标签，会按PVID进入VLAN5；同AP的NGBOSS对照报文携带VLAN2标签。修复前后核心端口配置未变，故不应通过把PVID改成3来掩盖问题。

本次实际修复只重新下发F01的NGR绑定：

1. 保存8台AP、16个频段的原NGR绑定记录；临时关闭NGR自动绑定，但保留已有绑定。
2. 筛选F01，仅移除其2.4GHz和5GHz的NGR绑定，再按原参数加回。手动加回时页面默认VLAN0，必须逐项明确启用VLAN绑定并设为3，不能只点击“绑定”就视为完成。
3. 恢复原来的自动绑定全部射频、单VLAN3设置，读回8台AP的16条绑定值并与变更前比较；其他7台AP的绑定值保持一致。完成AC全局保存。没有修改其他SSID、无线密码、核心端口或重启AP。
4. 让同一终端在F01附近关闭再开启Wi-Fi，直接新加入NGR；同时用AC新接入事件、核心18号口MAC学习位置和DHCP标签核对，排除漫游及旧租约。
5. 停止临时抓包、删除临时ACL，并读回确认清理完成；原始抓包、失败记录、配置比较和SHA-256清单保留在私有运维目录。

抓包与客户端验收结果：

| 项目 | 本次结果与边界 |
| --- | --- |
| 新接入身份 | 13:01:12（UTC+8）AC记录终端成功接入F01的NGR 5GHz，为新接入而非漫游 |
| DHCP标签 | 13:01:16.804的目标终端UDP68→67报文含`81 00 00 03`，即802.1Q VLAN3；核心local-host抓包仅保留64字节头部，不声称捕获完整DHCP交互 |
| IPv4与二层路径 | 终端取得`192.168.3.x`，核心将其业务MAC学在VLAN3、18号口；旧VLAN5 ARP／租约残留不能作为本次获址依据 |
| IPv6与实际流量 | 观察到VLAN3当前前缀的全局IPv6、双向IPv6 DNS及公网IPv6 HTTPS数据，另有双向IPv4公网流量；边界到终端的LAN IPv6探测3发3收 |
| 用户验收 | 关闭蜂窝数据后test-ipv6.com为10/10，用户再次确认网页正常 |
| 验收范围 | 仅证明此次F01 NGR 5GHz新接入；2.4GHz虽已配置，未单独完成新接入验收。不代替全部AP、长期稳定性或隔离策略复测 |

此次证据支持“AC保存的绑定与F01实际生效状态不一致，重新下发后恢复”。尚未区分配置未成功传输、AP未应用或固件运行机制异常，不能直接定性为不支持VLAN或已确认的固件缺陷。

排查中另发生一次误点复合操作栏、将测试终端加入黑名单的操作失误；用户解除后已核对黑名单为空。这解释当时的“无法加入NGR”和无目标DHCP报文，不是原始VLAN映射故障的原因。后续只点击明确的单项操作，抓包前先核对接入认证是否成功。边界侧一轮抓包因未覆盖新接入时刻而得到0包，也未计作通过证据。

### 3.5 NGX无法获取VLAN4地址（2026-10-24）

NGX绑定VLAN4，但15–22号AP Trunk此前仅放行2／3／5／100，VLAN4仅存在于QNAP B上联和nanopc的24号口，客户端无法到达地址服务器。只读核对确认nanopc的DHCPv4和rdhcpd运行正常，VLAN4 OSPFv3邻居为Full。

修复前保存8个AP口的允许列表并准备独立回退；每口仅增加`port trunk allow-pass vlan 4`，保留PVID5、其他VLAN和已有ACL，不修改AC绑定、地址服务或重启AP。读回8口均为Tagged4后，让指定终端在F10／19号口新接入NGX；核心MAC表确认其位于VLAN4，nanopc分配VLAN4 IPv4且网关为`.4.1`。IPv6最初尚未显示，随后无需其他配置修改即恢复，用户确认test-ipv6.com为10/10。rdhcpd日志同时保留该终端完成DHCPv6租约的记录，但未把服务端分配记录单独当作客户端配置成功的证明。核心配置已保存。

首轮被动抓包因诊断SSH中转空闲超时中止，未作为“没有RA”的证据；原失败与后续记录保留在私有目录。验收仅覆盖此次F10终端，不推定其他AP的NGX业务均已单独测过。

## 4 双栈路由、隔离与前缀变化

### 4.1 服务归属

| 服务 | 当前分工与核对 |
| --- | --- |
| VLAN2 DHCPv4 | 核心接口池，网关`.2.253`，DNS使用实际可达服务 |
| VLAN2 IPv6 | 核心PD／RA与WAN B回程；核对租约、PIO、M/O、RDNSS和实际默认路由 |
| VLAN3／4地址服务 | 各自边界保留原有服务，不再开第二套 |
| VLAN5 | 核心全局DHCP池`vlan5_ap`，网关`.5.253`；AC100 `.5.1`只管理AP，不提供地址分配 |
| VLAN100 | 当前核心网关和DHCP保留，直至全部业务依赖迁移 |

两条边界的OSPF／OSPFv3邻居、默认路由、委派前缀回程及防火墙必须一致；不能加静态默认路由掩盖邻居失败。Mac有线／无线同时在线时先核对实际出口，不能用经A线的成功探测证明B线正常。

### 4.2 隔离策略

已部署策略结构的脱敏示例见[双栈隔离模板](../deployment/network/huawei-b-vlan2-vlan4-isolation.cli.example)。示例使用文档IPv6前缀和虚构管理主机地址，不是可直接执行的现网脚本。

VLAN2默认拒绝访问内网普通地址，只按审核范围放行DNS与精确管理例外。目标固件不支持一个traffic policy混合IPv4／IPv6 ACL分类器，因此分为：

| 接口方向 | 作用 |
| --- | --- |
| Vlanif2入方向 | IPv4精确允许例外优先，随后拒绝内网目的 |
| Vlanif2出方向 | 精确回复例外优先，随后拒绝VLAN4来源 |
| Vlanif4出方向 | IPv6拒绝到受限内网前缀 |
| Vlanif4入方向 | IPv6拒绝受限来源到内网前缀 |
| Vlanif3入／出方向 | 最近备份另有A3_IN6／A3_OUT6附加IPv6隔离；保留并单独核对，不被B侧示例覆盖 |
| Vlanif100出方向 | V100_OUT4限制VLAN3来源到VLAN100：指定管理Mac优先允许，DNS回包及现有HomeSense连接保留，其余VLAN3来源拒绝 |

`if-match`分类器与deny行为表达隔离；不能用ACL的deny条目冒充需要放行的例外。顺序以已核对的precedence为准。保存前后都要读回受影响方向的全部应用记录、运行／启动配置差异，并分别测允许和拒绝方向。此前B侧四方向的success只证明当次范围，不自动证明A侧附加策略；本次未重新执行B侧四方向数据面测试。

2026-10-24补充验收范围为VLAN3到VLAN100的IPv4访问。NanoPi5的DHCP Option121同时保留AC的`/32`路由和默认路由，新增`192.168.0.0/24 → 192.168.3.253`；支持该选项的客户端续租后生效。指定管理Mac通过有线网卡MAC固定DHCP租约，核心按其固定IPv4放行，真实绑定值留在私有记录。已确认该Mac的DHCP ACK包含新路由、访问两台485网关及录像机成功、另一VLAN3来源被核心丢弃，HomeSense既有连接保持；核心7条策略均为success并已保存。该限制针对跨VLAN转发的设备访问，不等同于管理CPU保护或同VLAN终端隔离，也不包含GVS的`10.255.195.x`网络。

### 4.3 IPv6前缀变化保护

实机IPv6 ACL目的匹配只接受字面地址／长度或any，不能直接引用PD名字。当前没有前缀变化时自动更新ACL、自动暂停转发的实现。

1. 发现运营商PD变化时，先按获批流程暂停VLAN2 IPv6转发，避免旧ACL对新地址失配。
2. 读取两条WAN当前授权前缀、边界LAN前缀、新核心获租前缀、租期和回程；不从历史文档复制全球前缀。
3. 更新本次允许范围内的ACL及边界回程／防火墙集合，确认不会把A／B来源混用或误放行。
4. 用单独客户端验证双向隔离、DNS、公网IPv6、续租与前缀撤回，再恢复转发并保存。无证据时不标为完成。

## 5 后续迁移与VLAN100维护

### 5.1 尚未完成的迁移

`.0.10→.1.10`、PE11到VLAN2、NAS直连X3／X4、桌面交换机接入均是后续项目。开始前重新登记依赖、接口、地址、标签及回退，不能在当前端口表上把目标写成已完成。尤其HomeSense仍连接`.0.10:8443`；网关地址和服务配置必须在单独授权的发布中一致变更。

EA-5备份若仍使用`.0.x`，也属于VLAN100业务依赖。全部迁址或退役后，才可以关闭Vlanif100网关和原DHCP、保留VLAN100二层定义，并撤销不再需要的常驻标签；此前不执行这一步。

### 5.2 将来临时维护窗口

确认VLAN100已无业务依赖后，才使用[临时维护示例](../deployment/network/huawei-vlan100-maintenance.cli.example)，并重新核对当前固件语法及双向／CPU隔离。

- 一次只接一台缺省地址设备，核对地址冲突；优先按实际需要用有线维护口。
- 若启用指定AP维护SSID，记录本轮新增标签、AP选择、临时SVI与地址池，管理5和原业务成员保持。
- 临时DHCP不得发布网关、DNS或默认路由；静态保留和客户端地址不会因服务关闭立即自动消失，结束时主动清理。
- 测试选项、隔离、唯一DHCP／RA来源、目标设备访问及公网不可达；任一不符即停止。
- 结束时关闭临时服务和SSID，移除本轮新增且不被其他业务使用的标签，恢复端口PVID并核对服务已退出；不把临时SVI开放状态保存为开机默认。

| 范围 | 已有依据 | 剩余核对 |
| --- | --- | --- |
| 新核心接管与边界直连 | 配置、用户迁线及最近链路／邻居记录 | 变更后的客户端续租及长时间稳定性 |
| AP端口与最终命名 | 2026-10-24实时读回15–22全部Up；18／19为2.5G，其余1G | 速率快照不证明长期无断线，逐AP业务仍分别登记 |
| F01的NGR绑定修复 | 新接入DHCP Tagged3、VLAN3 IPv4／IPv6、公网双栈及用户10/10和网页正常 | 此次为5GHz新接入，2.4GHz及长期稳定性尚未独立验收；未复测隔离 |
| QNAP与管理入口 | 现用DAC、标签及本地维护路径记录 | QSS管理迁到5尚未验证，不顺手执行 |
| 双栈隔离 | 四方向策略应用及此前客户端测试 | PD变化保护与自动化仍未完成 |
| HomeSense | rev52实际配置与已部署程序只读核对 | 现场接管按[独立清单](control4-takeover-checklist.md)，不以网络验收补签 |

变更失败只恢复本次受影响设备与已保存设置；涉及重复网关或环路时先隔离新路径，再恢复已核对的旧路径。不要把旧核心全套三层服务、旧聚合和临时线一起恢复。配置、配对、凭证及独立维护入口均须保留。
