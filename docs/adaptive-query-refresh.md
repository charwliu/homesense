# 延期刷新与通信告警

服务端通过已有长连接接收反馈、向原生 App 推送状态；App 不通过设备轮询维持状态。

- 初始化读取完成后，使用已发布的自适应刷新策略。组件确认的短时 `max_age_ms` 不再成为永久查询订阅。
- 新控制指令仅为关联输出安排有截止时间的确认读取；已有真实反馈满足条件后结束确认。普通查询回复或相同值的重复反馈不会重新触发密集扫描。
- 初始化查询保留。普通周期从300秒开始；周期内没有面板或控制活动，依次延长为600、1200、2400、4800、7200秒，封顶7200秒。面板按下／释放或新的实际控制命令恢复300秒；模块主动状态反馈和查询回复只更新状态，不重置周期。
- 每条总线仅有一个未完成的查询槽。新活动保留当前扫描进度；空闲时重设下一轮到期时间，不能因此立即开始全屋扫描。命令关联的有限确认读取独立于普通周期，不扩大为永久查询订阅。
- 查询超时也按倍增规则退避，未完成的一轮结束之后才安排下一轮；即使该轮不足以生成完整新鲜证明，也不会立即重开扫描。新控制可解除其关联模块的旧退避，获取本次指令的反馈。
- 一次查询及其原有重试算一个失败轮次。同一通道连续三个轮次未响应后生成 `module_feedback_timeout`，记录次数、首次和最近时间；向有该设备读取权限的 App 推送告警。仅收到该通道有效反馈才清除告警并记录恢复。
- 已确认场景的持续活动使用自适应观测有效期；尚未确认的命令保持原有严格确认条件。等待、查询发送和 App 读取都不刷新物理观测时间；重启、撤权、代次变更和矛盾反馈仍使旧推断失效。

告警沿现有 WSS 状态流发送，App 展示设备名称和错误。该功能不依赖系统后台通知权限，也不代表 APNs 后台通知服务。

上述300～7200秒策略已随本轮程序更新上线。旧配置在Live运行时也遵守这两个界限，无需改写房间或设备范围；模拟环境仍允许显式短虚拟时钟。

此前R9针对性冒烟覆盖延期与退避、单轮扫描、组件所有权、按键避让、设备新鲜度、连续失败及恢复，共82项Linux测试，并通过13步门厅场景和联动LED回环、原生App告警测试。这些是历史结果。本次按先通过离家原失败场景、再完整回归及发布的顺序完成：Mac1690项及严格Clippy、Linux库687／HAP3、35组154步顺序私有回环、12项原生实际方法通过。早期重叠批次失败保留，此结果不证明多实例并行负载资格。详见[回归记录](evidence/stage-e-browser/away-response-refresh-qualification.json)。
