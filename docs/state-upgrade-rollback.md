# 状态升级与完整回退

数据库格式升级后，旧程序可能拒绝新库。回退必须同时恢复旧程序、服务配置和完整状态快照；只切换旧二进制不能恢复旧格式。

在既有发布授权范围内，先固定候选程序、源清单、配置版本和维护步骤。停止服务并确认进程、监听和数据库写入租约均已释放，再保存完整状态目录、候选可能修改的外部文件、旧服务单元和旧二进制位置。使用相对路径清单校验快照：文件内容哈希、类型、权限、属主、链接目标及目录本身的元数据均须覆盖。

候选失败时，先停止候选并保留失败状态，再恢复旧程序和完整快照。合成演练验证的复制方式是：

```sh
rsync -a --checksum --delete -- "$rollback_snapshot/" "$stopped_state/"
```

这里的两个目录必须来自已核对的维护清单，目标保持停机。`--delete` 清除失败候选新增的文件；`--checksum` 确保覆盖同大小、同修改时间但内容不同的数据库。普通 `rsync -a --delete` 会跳过这类文件，不能作为完整状态恢复的依据。

恢复后先逐项比较完整清单和数据库内容，再启动旧程序。重新核对活动配置、HAP 长期身份及配对、Web 授权、命令账目、可信 HTTPS 与服务就绪。正常启动可以更新 HAP 配对状态标记和旧命令的恢复状态；这些变化须按字段和实现核对，不能将身份数据或原命令的不变字段一并排除。

2026-10-16 的隔离演练使用现有正式 Linux 程序、回环假网关及合成状态。第四次尝试实际漏恢复了同大小、同秒级修改时间的数据库，Root 只读核查其恢复后版本头仍为 27。第六次加入固定同大小、同精确时间戳反例，并采用内容校验恢复，27 项清单的字节、权限、属主和链接恢复一致；旧程序重新打开版本 26，非空合成配对和 Web 凭据保持。该主机的 rsync 未保持纳秒级修改时间，原始值和差异均保留。

这证明回退机制，尚不证明未来真实 schema27 候选的升级及回退。该候选交付后仍须对其实际迁移重新验收。本轮没有读取或修改现网状态，没有停止 E2 或操作现场设备。详见[独立核查](evidence/stage-e-browser/state-tree-rollback-root-check.json)。
